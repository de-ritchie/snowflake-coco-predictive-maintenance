# Project Instructions

## Overview

SnowComotive — Predictive Maintenance & OEE Command Center. A hackathon submission demonstrating Cortex Code (CoCo) across the full planning→development→execution→testing lifecycle. Design docs: `docs/01-BRD.md` through `docs/04-*-LLD.md` (11 LLD modules), backlog: `docs/05-Epics.md`. Jira project **SH** (`chirajpepz.atlassian.net`) mirrors the backlog doc — `docs/05-Epics.md` is the source of truth, Jira is the working view.

## Architecture: skills vs. agents (read this before touching either folder)

**Skills** (`.cortex/skills/*/SKILL.md`) are markdown instructions injected into the *current* conversation — no isolated context, no separate dispatch. Reserved for purely mechanical, repeatable procedures with no real judgment call:
- `dev-workflow` — querying the Jira board (JQL), branch naming/creation, committing, opening a PR, attaching a Jira comment, status transitions. Referenced exclusively by `Jira-Triage-agent` — no other agent touches Jira or mutates git, so no other agent needs this skill.

**Agents** (`.snowflake/cortex/agents/*.md`) are real subagents — own isolated context, dispatched via the `task` tool, `model: claude-sonnet-5`. Reserved for actual reasoning/judgment work. **Content agents never touch Jira or git**; **`Jira-Triage-agent` never writes implementation content** — that split is the whole point of this design:
- `Design-agent` — brainstorms any implementation story (dbt model, Streamlit page, Snowpark script, agent/tool config, ops script) with the user, freezes a design doc to `docs/designs/SH-<key>-<slug>.md` once explicitly confirmed. Optional for trivial stories. No code, no Jira/git touch.
- `Developer-agent` — implements strictly against the frozen design doc (any story type, not dbt-only). Leaves changes uncommitted, no Jira/git touch.
- `Reviewer-agent` — reviews the working-tree diff (no commit required) against the frozen design doc + whatever named correctness invariants this project's FRD/LLD actually calls out (e.g. join-timing/leakage rules, incremental-window direction rules), runs `dbt run`/`dbt test` or other domain-appropriate verification. Reports in chat only, re-invokable any number of times, never edits code, never touches Jira/git.
- `Documenter-agent` — reconciles the design doc with what was built, updates `schema.yml`/`CHANGELOG.md`. Leaves changes uncommitted, no PR, no Jira/git touch.
- `Jira-Triage-agent` — the *only* agent that touches Jira or mutates git state. Front door: discusses backlog priority/dependencies with the user, picks the next story, creates its branch, stops. Callable again any number of times mid-story to commit on request. Back door (on request): opens the PR, posts one consolidated Jira comment, moves the story to Review, and later to Done once the user confirms the merge. Replaces the old `board-triage` skill and the old dbt-only/non-dbt-lane split entirely — there is now one lane (`Design→Developer→Reviewer→Documenter`) for every story type, not two.
- `Genesis-agent` — bootstraps a *brand-new* project: brainstorms a problem statement with the user through cascading freeze checkpoints, writes the BRD→FRD→HLD→LLD doc stack from scratch, then (optionally) scaffolds genericized copies of the other 4 agents + `Jira-Triage-agent` + `dev-workflow` into the new project. This is what makes the whole toolkit portable beyond this one repo — everything else here assumes `docs/*.md` already exists; this is what creates it.

**Critical constraint**: subagents cannot spawn other subagents. There is no auto-orchestration — sequencing through Design→Developer→Reviewer→Documenter (looped through as many times as needed) → `Jira-Triage-agent` (or through Genesis-agent's own 5 stages) is driven manually by the user, one agent at a time.

**Table-agnostic by design**: none of the 5 SDLC agent prompts hardcode a specific table/column/schema/FR-ID — that was a real bug fixed on 2026-08-26 (they used to reference this project's specific FR-PL-03/FR-FS-09/FEAST-macro naming despite claiming otherwise). Specifics always come from `docs/03-HLD.md` / the relevant `docs/04-*-LLD.md` module for the story at hand, or the frozen `docs/designs/` doc once one exists. If a prompt needs updating because the docs changed, update the prompt's *pointer* to the docs, not embedded specifics — this is what lets `Genesis-agent` copy these files verbatim into a different project without editing them.

**Known limitation**: `dev-workflow` is NOT yet parameterized — it hardcodes this repo's Jira cloudId/project key directly in prose. `Genesis-agent`'s scaffold step copies it with placeholders for a new project's Jira details, but that's a manual fill-in, not a clean config file. Flagged as a possible future improvement, not built.

## Local dev environment

- **Package management: `uv`**, not pip/conda/poetry. Dependencies live in `pyproject.toml` (+ `uv.lock`, committed). Run scripts via `uv run <script>.py`, add deps via `uv add <pkg>` — never call `pip install` directly. The `.venv` is already provisioned; agents should not create or rebuild it unless a dependency is genuinely missing (check `pyproject.toml`/`uv.lock` first).
- **Snowflake connection: `manage.py` defaults to a named connection `snow-coco`, but no such profile currently exists in `~/.snowflake/connections.toml` on this machine — you MUST set `SNOWFLAKE_CONNECTION_NAME` explicitly or every `manage.py`/dbt invocation fails with a connection-not-found error.** The two profiles that actually exist and are used day-to-day are `snow-co-cat-alyst` (no role pinned — bootstrap connection for `manage.py up`/`down`/`post-setup`/`authorize-jira-mcp`, must work even before `snowcomotive_role` exists or right after a teardown) and `snow-co-cat-alyst-snowcomotive` (role pinned to `snowcomotive_role` — day-to-day ad hoc queries). See `scripts/README.md` "Local/ad hoc connections" for the exact `connections.toml` snippet and why two separate profiles are needed. Always run `manage.py` as `SNOWFLAKE_CONNECTION_NAME=snow-co-cat-alyst uv run python manage.py <command>` (or export it for the session) until/unless a `snow-coco` profile is added back. Requires the `secure-local-storage` extra on `snowflake-connector-python` (via `keyring`) to cache the OAuth/session token locally.
- **Lifecycle scripts: run via `manage.py up` / `manage.py down` only — the `snow` CLI is not used in this project.** `manage.py` (repo root, `typer`-based CLI) chains the numbered `scripts/0N_*.sql` files (plus the thin-data generator on `up`) through one connector session (OAuth or password auth depending on the profile — no MFA/TOTP passcode needed). The `snow` CLI's MFA/TOTP-based connection required a fresh passcode on every single invocation — an explicitly rejected workflow — so it was dropped entirely in favor of `snowflake-connector-python` (see `docs/designs/1 - SH-2-11-upload-load-into-raw.md` §8 for the full writeup). Do not add `snow sql -f` invocations or `snow` CLI dependencies going forward; extend `manage.py` instead.
- **Re-running `manage.py up` against an account that isn't actually torn down can silently duplicate every RAW table's rows.** `03_setup_raw_load.sql`'s `COPY INTO` relies on Snowflake's native load-history dedup (keyed on filename+checksum), but the data generator embeds a fresh timestamp into same-named files on every run — a different checksum each time — so the dedup does NOT catch it. If `01_setup.sql`'s output says objects "already exist" instead of "successfully created," the environment has leftover state; run `manage.py down` first, then `up`, for a guaranteed-clean load. Confirmed live (2026-09-28): this produced a real `dbt test` failure (`unique_cons__fct_priority_score_equipment_id`) traced back through duplicated `raw.equipment`/`std__equipment`/`cons__dim_equipment` rows.
- Python scripts that aren't dbt models live outside `scripts/` (which is reserved for the numbered SQL lifecycle scripts, `scripts/0N_*.sql` — see `scripts/README.md`). Keep Python generator/ops scripts in their own top-level dir (e.g. `generator/`) to avoid mixing with that numbered SQL sequence.
- **dbt project: `predictive_maintenance_dbt/`** at repo root (project/profile name `predictive_maintenance_dbt`, not `dbt/`/`snowcomotive` as some early design-doc drafts assumed). `predictive_maintenance_dbt/profiles.yml` is committed in-repo (no secrets — `authenticator: oauth_authorization_code`, same Snowflake account as the `manage.py` connections above, but dbt manages its own token/session independently) and already verified via `dbt debug`; don't recreate it. Run via `manage.py up`'s `run_dbt()` step (`dbt run` / `dbt seed` / `dbt test`), or directly with `uv run dbt <command> --project-dir predictive_maintenance_dbt --profiles-dir predictive_maintenance_dbt`.
- **Real Jira ticketing exists, via a Snowflake `EXTERNAL MCP SERVER` wrapping Atlassian's hosted MCP endpoint — not a simulated/native-table store (that path was retired, SH-62 amendment, 2026-09-28).** `maintenance_supervisor_agent` is the only agent with this capability (`mcp_servers: [snowcomotive.cons.jira_mcp_server]`) — it creates real tickets, with best-effort dedupe-before-create, always targeting the **`SUP`** project (see the Jira-projects bullet below). `production_planner_agent`/`plant_manager_agent` have zero ticketing capability by design (Snowflake's `external_mcp` servers expose their whole tool set or nothing — no per-agent subset is possible). The integration/server objects (`jira_mcp_integration`, `snowcomotive.cons.jira_mcp_server`) are account/schema-scoped and NOT part of `manage.py up` — provisioned standalone via `scripts/07c_setup_jira_mcp.sql`, and OAuth consent is a one-time-per-account human step via Snowsight's Agent UI or Snowflake CoWork's Connectors UI (`manage.py authorize-jira-mcp` only does a read-only existence check and points at those UIs — scripted OAuth was tried and abandoned). See `docs/designs/SH-62-mcp-swap-jira.md` for the full design/rationale.
- **Dynamic-table freshness is a single parameter, not 6 hardcoded values (SH-72, 2026-09-28).** Only `cons__fct_priority_score` (the pipeline's one leaf, the only table anything outside the dbt-ref chain actually queries) has an explicit `target_lag`, sourced from the dbt var `target_lag` (`DYNAMIC_TABLE_TARGET_LAG` env var, default `'1 hour'`) — set it via `manage.py up --target-lag "<value>"`. Every upstream table (`std__sensor_reading` → `cons__fct_sensor_reading` → `feast__fct_sensor_features_inference` → `cons__fct_anomaly_result` → `cons__fct_rul_prediction`) is hardcoded `target_lag='DOWNSTREAM'` and derives its cadence from the leaf automatically — do not give any of those 5 tables their own explicit `target_lag` unless a future story genuinely needs independent freshness control (none currently do — verified via full `ref()` cross-check, single linear chain, one external consumer). Snowflake's real minimum `target_lag` is 60 seconds (not 30s). Confirmed live (2026-09-28): the whole 6-table chain auto-refreshes end-to-end on a `SCHEDULED`/`SUCCEEDED` cadence with no manual `dbt run` needed once `manage.py up` has applied the config once. See `docs/designs/SH-72-parameterize-target-lag.md`.
- **Never invoke a bare `dbt` directly — always go through `uv run dbt <command>` (or `source .venv/bin/activate` first if you must run several dbt commands in a row).** This machine also has a standalone dbt-fusion (Rust) binary at `~/.local/bin/dbt` (`dbt 2.0.6`) sitting earlier on `$PATH`, and it does **not** support `authenticator: oauth_authorization_code` (`[error] Unsupported authenticator: oauth_authorization_code`) — a different, incompatible dbt from the one this project actually needs. `uv run dbt ...` always resolves to the project's real `dbt-core 1.12.3`/`dbt-snowflake 1.12.0` pinned in `.venv`/`pyproject.toml`, sidestepping `$PATH` entirely — this is the same "use `uv`, not a bare interpreter/binary" rule as the package-management bullet above, just for dbt specifically.

## Guidelines

- Never implement a story's work directly on `main` — every story gets its own branch (`dev-workflow` skill's naming convention: `<type>/SH-<epicNum>-<storyNum(s)>-<slug>`).
- Never merge a PR without the user's explicit go-ahead — that's the human gate this whole workflow is built around (FR-SDLC-02).
- `docs/05-Epics.md` is the backlog source of truth; if Jira and the doc ever disagree, the doc wins — fix Jira to match, or update the doc explicitly and say so, never let them silently drift.
- Two Jira "projects" exist conceptually — the **`SH`** Kanban board (this repo's own dev tracking, A10, on `chirajpepz.atlassian.net`) and the **`SUP`** Jira Service Management project (A5, live since SH-53/2026-09-27, touched only by the *deployed* agents at runtime for real maintenance tickets via the Jira MCP connector — see the ticketing bullet above). Don't conflate them; real tickets must always land in `SUP`, never `SH`.
