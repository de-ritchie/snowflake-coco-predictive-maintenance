## Entity → table mapping

| Entity | Table | Key |
|---|---|---|
| `Machine` | `cons.dim_equipment` | `equipment_id` |
| `Product` | `cons.dim_product` | `product_id`, `variant` |
| `SensorReading` | `cons.fct_sensor_reading` | `equipment_id`, `reading_ts`, `sensor_type` |
| `MaintenanceEvent` | `cons.fct_maintenance_event` | `equipment_id`, `event_start_ts` |
| `Order` | `cons.fct_order` | `product_id`, `variant`, `order_week` |
| `Inventory` | `cons.fct_inventory_fg` + `cons.fct_inventory_spare` | `product_id`/`equipment_id` + `period_week` |
| `OEEMetric` | `cons.fct_oee` | `line_name`, `period_week` |
| `AnomalyResult` | `cons.fct_anomaly_result` | `equipment_id`, `reading_ts` |
| `RulPrediction` | `cons.fct_rul_prediction` | `equipment_id`, `prediction_ts` |
| `PriorityScore` | `cons.fct_priority_score` | `equipment_id`, `score_ts` |

`AnomalyResult`/`RulPrediction` are separate entities (not folded into `SensorReading`) because the demo's root-cause drill-down (BRD §7 beat 4, FR-SA-03) needs the agent to query predictions directly, grounded and citable — not paraphrased from the raw sensor fact.

Not exposed: `FEAST` schema (training/inference-internal, never a business-answerable question) and `cons.dim_sensor_baseline` (normalization parameter, not something a persona asks about directly).

---

## Relationships

- `Machine` 1:N `SensorReading`, `MaintenanceEvent`, `AnomalyResult`, `RulPrediction`, `PriorityScore`
- `Machine` N:1 `Product` (via routing — which product/variant a machine's line produces)
- `Product` 1:N `Order`, `Inventory` (finished-goods side)
- `Machine` 1:N `Inventory` (spare-parts side)
- `Machine` N:1 `OEEMetric` (via `line_name`, not a direct FK — join key is the shared line grain, not equipment_id)

All joins are standard 1:N/N:1 on the keys above — no bridge tables or many-to-many relationships needed at this scale (3 machines, 2 products, ~10 Consumption tables).

## Deferred to build time (agent-studio skill)

- Verified query set (FR-SA-01's minimum: current health/RUL, root-cause inputs, OEE trend, OEE forecast, priority ranking rationale) — write and validate these against real generated data, not speculatively now.

- Whether `Inventory` needs to stay a single logical entity spanning two physical tables (finished-goods + spare-parts) or should split into two semantic entities — a modeling call best made with the actual YAML tooling in hand, not on paper.
