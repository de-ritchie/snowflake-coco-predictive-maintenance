## 1. Setup script (FR-OPS-01)

```sql
-- Role, warehouse, database, schemas, stage
CREATE ROLE IF NOT EXISTS snowcomotive_role;
CREATE WAREHOUSE IF NOT EXISTS snowcomotive_wh WAREHOUSE_SIZE = 'XSMALL' AUTO_SUSPEND = 60 AUTO_RESUME = TRUE;
CREATE DATABASE IF NOT EXISTS snowcomotive;
CREATE SCHEMA IF NOT EXISTS snowcomotive.raw;
CREATE SCHEMA IF NOT EXISTS snowcomotive.std;
CREATE SCHEMA IF NOT EXISTS snowcomotive.cons;
CREATE SCHEMA IF NOT EXISTS snowcomotive.feast;
CREATE STAGE IF NOT EXISTS snowcomotive.raw.landing_stage FILE_FORMAT = (TYPE = PARQUET);
GRANT ALL ON DATABASE snowcomotive TO ROLE snowcomotive_role;
```

```python
# Data generation — re-use existing dataset if supplied (NFR-05), else generate
if not args.reuse_dataset_path:
    run_snowpark_generator(seed=args.seed, output_dir=args.output_dir)   # FR-DG-12, Module 2
    dataset_path = args.output_dir

    dataset_path = args.reuse_dataset_path

upload_to_stage(dataset_path, "@snowcomotive.raw.landing_stage")
```


## 2. Pipeline run, phase 1 — features (FR-OPS-02)

```bash
dbt run --exclude tag:inference+
dbt test --exclude tag:inference+
```

`tag:inference+` selects the model-inference dynamic tables (`cons.fct_anomaly_result`, `cons.fct_rul_prediction`) and everything downstream (priority score) — excluding them here builds Raw → Standardized → Consumption → `FEAST` (Modules 1/3/4) without touching anything that references a not-yet-trained model.

## 3. Model training (FR-OPS-02a)

```sql
CALL snowcomotive.cons.sp_train_isolation_forest();   -- Module 5 §1
CALL snowcomotive.cons.sp_train_rul_aft();            -- Module 5 §2
```

Must run after step 2 (needs `feast.fct_sensor_features_train` and `feast.training_dataset_*` built) and before step 4 (the inference dynamic tables reference these models by name at `CREATE` time — FR-OPS-02a's whole reason for existing as a separate, ordered step).

## 4. Pipeline run, phase 2 — inference & downstream (FR-OPS-02b)

```bash
dbt run --select tag:inference+
dbt test --select tag:inference+
```

This is the step that fails with a clear "model not found" error if run before step 3 — expected and acceptable (FR-OPS-06 requires re-runnability, not silent success on out-of-order execution).

## 8. Idempotency (FR-OPS-06)

- All DDL above uses `CREATE OR REPLACE` or `CREATE IF NOT EXISTS` — re-running setup against an existing environment doesn't fail or duplicate objects.
- `COPY INTO`'s native load-history tracking (FR-PL-09) makes re-running step 1's data load idempotent without custom dedup logic — already established in Module 1/FRD, restated here since this is where it's actually invoked.
- Jira project creation checks existence first (§1) rather than relying on a Jira-side uniqueness error.
- Running phase 2 (§4) before phase 3 (§3) fails loudly (model not found) rather than silently — acceptable per FR-OPS-06's "safe to invoke out of order" meaning "doesn't corrupt state," not "succeeds regardless of order."
