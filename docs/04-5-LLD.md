## 1. IsolationForest (anomaly detection)

**Input features** (from `FEAST.TRAINING_DATASET_ISO`, `dataset_split = 'train'`): now genuinely joint per tick after Module 4's wide-format pivot — one row per `(equipment_id, reading_ts)` with `vibration_z`, `vibration_rolling_1h_z`, `vibration_rolling_8h_z`, `vibration_rolling_24h_z`, `vibration_rolling_7d_z`, and the same 5-column pattern for `temperature_*` and `rpm_*` — 15 sensor feature columns total, all 3 sensor types seen by the model simultaneously per row (satisfies BRD's "joint input features" requirement — resolved during this module's spec, previously a long-format gap flagged and fixed in Module 4).

**Hyperparameters** (MVP defaults, tune empirically once trained):

```python
IsolationForest(
    n_estimators=100,
    contamination=0.05,      # ~5% of ticks expected anomalous — matches the ~10-15% unexplainable-breakdown
                              #  rate (Module 2 §3) being a subset of a broader "unusual reading" population
    random_state=42,
)
```

**Training** (Python stored procedure or Snowpark ML notebook cell — training is not latency-sensitive, either works; stored procedure chosen for consistency with FR-OPS-02a's scripted pipeline run):

```python
train_df = session.table("feast.training_dataset_iso").filter(col("dataset_split") == "train")
sensor_feature_cols = [
    "vibration_z", "vibration_rolling_1h_z", "vibration_rolling_8h_z", "vibration_rolling_24h_z", "vibration_rolling_7d_z",
    "temperature_z", "temperature_rolling_1h_z", "temperature_rolling_8h_z", "temperature_rolling_24h_z", "temperature_rolling_7d_z",
    "rpm_z", "rpm_rolling_1h_z", "rpm_rolling_8h_z", "rpm_rolling_24h_z", "rpm_rolling_7d_z",
]
model = IsolationForest(n_estimators=100, contamination=0.05, random_state=42)
model.fit(train_df, input_cols=sensor_feature_cols)
```

**Model Registry logging**:

```python
mv = registry.log_model(
    model,
    model_name="isolation_forest_model",
    version_name=f"v_{run_date}",
    sample_input_data=train_df.limit(1000),   # required for explainability, FR-FS-00c
    options={"enable_explainability": True},
)
```

Snowpark ML Modeling's built-in estimators default `volatility=IMMUTABLE` for deterministic methods (FR-FS-00f) — no explicit override needed here, unlike the RUL model (§2).

## 2. RUL AFT model

**Input features** (from `FEAST.TRAINING_DATASET_RUL`, `dataset_split = 'train'`): the same z-scored rolling features (§1) **plus** `hours_since_last_service`, `hours_since_install`, and the anomaly model's own output (`is_anomaly`, `anomaly_score`) joined in from `cons.fct_anomaly_result` at training-set-build time (Module 4's open item — not yet wired into `FEAST.TRAINING_DATASET_RUL`'s SQL; flagged there and restated here since this module is where it actually gets consumed).

**DMatrix construction** (raw `xgboost`, not Snowpark ML's `XGBRegressor` — FR-FS-02):

```python
import xgboost as xgb

train_pdf = session.table("feast.training_dataset_rul").filter(col("dataset_split") == "train").to_pandas()

dtrain = xgb.DMatrix(train_pdf[feature_cols])
dtrain.set_float_info("label_lower_bound", train_pdf["y_lower"].values)
dtrain.set_float_info("label_upper_bound", train_pdf["y_upper"].fillna(np.inf).values)   # NULL -> +inf, FR-DG-11 censoring

params = {
    "objective": "survival:aft",
    "aft_loss_distribution": "normal",     # Weibull-generating process (Module 2 §4) -> normal AFT loss on log-time
                                            #  is the standard practical choice; log-normal is the closest AFT
                                            #  distribution family to a Weibull failure-time generator without
                                            #  requiring the extreme-value loss variant
    "aft_loss_distribution_scale": 1.0,
    "tree_method": "hist",
    "max_depth": 4,                        # shallow — feature set is small (~17-19 columns: 15 sensor z-score
                                            #  columns + hours_since_last_service/install + anomaly outputs),
                                            #  avoid overfitting on a few-hundred-cycle training set
}
booster = xgb.train(params, dtrain, num_boost_round=100)
```

**Model Registry logging** — custom/generic Python model path (raw `Booster`, not a Snowpark ML Modeling type), so `volatility` must be set explicitly (FR-FS-00f):

```python
from snowflake.ml.model import Volatility

mv = registry.log_model(
    booster,
    model_name="rul_model",
    version_name=f"v_{run_date}",
    sample_input_data=train_pdf[feature_cols].head(1000),
    options={
        "enable_explainability": True,
        "volatility": Volatility.IMMUTABLE,     # NOT the default for custom models — required for incremental
                                                 #  dynamic-table refresh (FR-FS-09) to work at inference time
    },
)
```

## 3. Evaluation (FR-FS-05)

```python
test_pdf = session.table("feast.training_dataset_rul").filter(col("dataset_split") == "test").to_pandas()
dtest = xgb.DMatrix(test_pdf[feature_cols])
pred_hours = booster.predict(dtest)

# Concordance index — primary metric, uses the full test set including censored rows
from sksurv.metrics import concordance_index_censored
c_index = concordance_index_censored(
    event_observed=test_pdf["y_upper"].notna().values,   # True = uncensored (failure observed)
    event_time=test_pdf["y_lower"].values,
    estimate=-pred_hours,   # higher predicted RUL should correspond to lower risk -> negate for c-index convention
)[0]

# MAE/RMSE — uncensored subset only, per FR-FS-05
uncensored = test_pdf["y_upper"].notna()
mae = mean_absolute_error(test_pdf.loc[uncensored, "y_lower"], pred_hours[uncensored])
```

Both metrics get logged as Model Registry metrics on the version (`mv.set_metric(...)`), and surfaced in the Streamlit Impact Statement view (FR-CC-07).

## 4. Explainability validation plan (FR-FS-00c/00d)

Two things to actually run and document at build time, not assume:

1. **IsolationForest**: call `MODEL(isolation_forest_model, LAST)!explain(...)` on a handful of known-anomalous and known-normal ticks from the test set. Check whether the returned per-feature Shapley values make intuitive sense against `decision_function`'s score (e.g., does a spike in `rolling_1h_avg_z` for the primary sensor of a known failure mode show up as the dominant contributor). Pass/fail is qualitative — there's no ground-truth attribution to check against.
2. **RUL model**: same call pattern, but on the custom `Booster`-wrapped model — first confirm `explain` is even callable for a model logged via the raw/generic Python path (not guaranteed by Snowflake's docs to work identically to the high-level XGBoost logging flow). If it errors or returns nonsensical output, fall back per FR-FS-00d: expose raw per-sensor z-score deviations alongside the anomaly score as the root-cause input instead, and drop the `explain_prediction` agent tool from scope (HLD §5 lists it as "pending validation").
