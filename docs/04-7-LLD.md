## 1. Shared: the Analyst tool (all 3 personas)

There is no `query_semantic_view` custom tool — Cortex Agents have a **built-in** tool type for this, `cortex_analyst_text_to_sql`, configured with the semantic view (Module 6) as a resource:

```yaml
tools:
  - tool_spec:
      type: "cortex_analyst_text_to_sql"
      name: "Analyst"
      description: "Answers questions about machine health, RUL, OEE, orders, inventory, and priority ranking using the SnowComotive semantic view."
tool_resources:
  Analyst:
    semantic_view: "snowcomotive.cons.oee_semantic_view"
    execution_environment:
      type: "warehouse"
      warehouse: "SNOWCOMOTIVE_WH"
      query_timeout: 30
```

Same `tool_resources` entry across all three agents (they share one semantic view, per BRD §3) — only the surrounding `tools` list and `instructions` differ per persona (§2-4).

## 2. Custom tool: `explain_prediction` (Supervisor + Planner)

Wraps a stored procedure that calls `MODEL(model_name, version)!explain(...)` for a given machine/timestamp (FR-FS-00d) — **pending validation** per Module 5 §4; ship without it if explainability testing fails, per FR-FS-00d's graceful-degradation path.

```yaml
tool_spec:
  type: "generic"
  name: "explain_prediction"
  description: "Returns per-feature Shapley contributions explaining why the model flagged a machine's current anomaly score or RUL prediction. Use when the user asks 'why' a machine is flagged, not just 'what' the prediction is."
  input_schema:
    type: "object"
    properties:
      equipment_id:
        type: "string"
        description: "The machine to explain, e.g. CNC_BORING_01"
      model:
        type: "string"
        description: "Which model's prediction to explain: 'isolation_forest' or 'rul_aft'"
    required: ["equipment_id", "model"]
tool_resources:
  explain_prediction:
    type: "procedure"
    execution_environment:
      type: "warehouse"
      warehouse: "SNOWCOMOTIVE_WH"
    identifier: "SNOWCOMOTIVE.CONS.SP_EXPLAIN_PREDICTION"
```

## 3. Custom tool: ticket creation (Supervisor: dispatch, Planner: escalation)

**Same underlying stored procedure, two different tool names/descriptions** — this is how FR-SA-02's "same API, different framing" gets implemented without duplicating logic: the orchestration instructions (per persona, §4) tell each agent which framing applies, not the tool itself.

**Duplicate-ticket check (FR-JR-04) happens inside the procedure, not the agent**: before creating anything, the procedure runs a live JQL check against Jira for an existing open ticket on `equipment_id`, or one closed within the tunable recent-window (Module 9). It returns one of three statuses — `CREATED` (new ticket_id/link), `ALREADY_OPEN` (existing ticket_id/link, no new ticket made), or `RECENTLY_CLOSED` (existing ticket_id/link, no new ticket made). The agent must report whichever status actually came back — instructed explicitly not to assume `CREATED` and not to paraphrase a dedup result as if a fresh ticket was filed.

```yaml
tool_spec:
  type: "generic"
  name: "create_jira_ticket"          # Planner's version: name = "request_jira_ticket", same schema/resource
  description: "Creates a Jira Service Management ticket for a machine needing maintenance, unless one already exists (open or recently closed) — in which case it returns the existing ticket instead of creating a duplicate. Only call when the user explicitly asks to file/create/request a ticket — never automatically."
  input_schema:
    type: "object"
    properties:
      equipment_id: { type: "string", description: "Machine needing maintenance" }
      predicted_rul_hours: { type: "number", description: "Predicted remaining useful life, from the RUL model" }
      priority_score: { type: "number", description: "Current priority score, 0-100" }
      root_cause_summary: { type: "string", description: "Plain-language root cause, grounded in sensor/model data" }
      requested_by_persona: { type: "string", description: "Maintenance Supervisor or Production Planner" }
    required: ["equipment_id", "predicted_rul_hours", "priority_score", "root_cause_summary", "requested_by_persona"]
    # Response (not input) includes: status ("CREATED" | "ALREADY_OPEN" | "RECENTLY_CLOSED"), ticket_id, ticket_url
tool_resources:
  create_jira_ticket:
    type: "procedure"
    execution_environment:
      type: "warehouse"
      warehouse: "SNOWCOMOTIVE_WH"
    identifier: "SNOWCOMOTIVE.CONS.SP_CREATE_JIRA_TICKET"
```

Fields match HLD §5's Jira ticket field list exactly (FR-JR-01) — no drift between the two documents.

## 4. Per-persona tool lists and instructions

| Persona | `tools` | `instructions.orchestration` (excerpt) |
|---|---|---|
| **Maintenance Supervisor** | `Analyst`, `explain_prediction`, `create_jira_ticket` | "For root-cause questions ('why is X flagged'), use explain_prediction after Analyst. Only call create_jira_ticket on explicit user request to file a ticket — never proactively (FR-JR-03)." |
| **Production Planner** | `Analyst`, `explain_prediction`, `request_jira_ticket` | "Frame ticket creation as an escalation/request, not a direct dispatch — this persona plans, it doesn't do hands-on repair. Prioritize OEE/forecast/demand framing over raw sensor detail." |
| **Plant Manager** | `Analyst` only | "Read-only rollup persona — no ticketing tool is configured, so never suggest filing a ticket; redirect the user to the Supervisor or Planner persona if asked." |

All three share the guardrail instruction from FR-SA-04: *"If sensor/prediction data for a requested machine is missing or stale, say so explicitly rather than fabricating a health/RUL value."*
