# LLD Module 2 — Data Generation Algorithm
## SnowComotive — Predictive Maintenance & Overall Equipment Effectiveness (OEE) Command Center

Status: Draft v0.1
Traces to: [02-FRD.md](02-FRD.md) Section B (FR-DG-01 through 12) | [04-1-LLD.md](04-1-LLD.md)

This module gives the executable formulas/parameters behind FR-DG-01-12 — concrete enough to implement directly, without repeating the FRD's rationale.

---

## 1. Calendar (FR-DG-01)

- 5-day work week (Mon-Fri), 3×8hr shifts = 24 operating hours/day.
- 10 fixed holidays/year (generic, not tied to a real jurisdiction) — hard non-working days regardless of backlog.
- A small residual idle chance (~2-3% per working day, independent of orders) still applies on top of whatever §7 derives — ordinary logistics/staffing variance, not demand-related.

Note: this section only covers what's *fixed* about the calendar. How many of a given working day's 24 hours a machine actually runs is derived from orders — see §7.

## 2. Machine sensor baselines (FR-DG-02)

| Machine | Vibration (mm/s RMS) mean / std | Temperature (°C) mean / std | RPM mean / std | Throughput (units/hr) |
|---|---|---|---|---|
| CNC Boring | 2.5 / 0.3 | 45 / 3 | 2,400 / 150 | 15 |
| CNC Milling | 3.0 / 0.4 | 48 / 3 | 3,200 / 200 | 15 |
| CNC Horizontal | 2.2 / 0.3 | 42 / 3 | 6,000 / 300 | 10 |

Reading noise: additive Gaussian, `noise_std = 0.3 × sensor's baseline std`, sampled independently per reading.

These mean/std values are the actual data populating `CONS.DIM_SENSOR_BASELINE` (Module 1) — normalization against them happens in the `FEAST` schema's `sensor_rolling_features` macro (Module 4), not during generation and not materialized as a column here.

## 3. Failure-mode signatures (FR-DG-03)

Each sensor has a **sensitivity** (0-1) per failure mode, controlling how much that sensor drifts as the underlying wear progresses. Mode is drawn per maintenance cycle (i.e., per stretch of operating hours between two consecutive service events).

| Mode | Probability | Vibration sensitivity | Temperature sensitivity | RPM sensitivity |
|---|---|---|---|---|
| Bearing wear | 28% | 0.8 | 0.6 | 0.1 |
| Tool/insert wear | 24% | 0.9 | 0.1 | 0.05 |
| Coolant/thermal | 20% | 0.05 | 0.9 | 0.05 |
| Servo/RPM instability | 18% | 0.15 | 0.05 | 0.85 |
| Unexplainable | 10% | — (no buildup; abrupt failure, see §4) | — | — |

**Primary sensor** for a mode = highest-sensitivity sensor (drives the Weibull failure-time draw and the "targeted" repair in §5). Servo/RPM instability is the RPM-alone signature (minimal vibration coupling, negligible temperature effect) — without it, RPM would never be the leading signal for any mode, leaving the sensor decorative.

## 4. Health degradation & sensor reading formula (FR-DG-04)

Per machine, per maintenance cycle: draw `mode` (§3), then:

```
T_fail ~ Weibull(shape=2.0, scale=λ_machine)   -- operating hours; λ_machine ≈ 500-800h, tune per machine so
                                                  cycles average a few weeks at 24 op-hr/day
```

For **explainable modes** (bearing/tool/coolant/servo), at elapsed operating hours `t` since cycle start (0 ≤ t ≤ T_fail):

```
H_s(t) = 1 - sensitivity_s * (t / T_fail)^2          -- per-sensor health, 1.0 = fresh
reading_s(t) = baseline_mean_s + (1 - H_s(t)) * amplitude_s + noise_s
amplitude_s = 4 * baseline_std_s                      -- how far a fully-degraded sensor can drift
```

For **unexplainable** mode: `reading_s(t) = baseline_mean_s + noise_s` for all `t < T_fail` (no precursor at all), then breakdown fires at `T_fail` — `T_fail` here drawn from `Exponential(mean=400h)` instead of the Weibull (no wear-out shape, matches a random exogenous cause).

Degradation accrues only during operating hours, and only as many hours per week as §7's order-derived schedule actually allocates — idle/holiday/capacity-shortfall time doesn't advance `t`.

## 5. Maintenance events & restoration (FR-DG-05, FR-DG-05a, FR-DG-06)

Two independent triggers, whichever comes first ends the cycle:

- **Scheduled PM**: due every 30 calendar days per machine — but *whether it actually happens on schedule* is gated by crew capacity (below), not automatic.
- **Breakdown**: fires when `t` reaches `T_fail` (§4). Always gets immediate crew attention, any day, bypassing the capacity constraint entirely — a stopped line is never queued.

**Crew capacity constraint (FR-DG-05a) — this is what creates the demo's counter-intuitive tension, not a difference in per-hour wear rate:**

```
Each week:
  1. Any breakdown on our 3 machines?  -> immediate repair, skip steps 2-4 for that machine.
  2. Background plant draw: Bernoulli(p=0.25)                    -- tune 0.20-0.30
     If true: the week's single crew slot is already consumed elsewhere in the
     plant (Casting, Drilling, Deburr, Coating, Assembly, etc. -- not simulated,
     just a probability standing in for their existence). No PM for our 3 machines
     this week, regardless of who's due.
  3. Otherwise, if >=1 of our 3 machines has PM due: the ONE machine on the
     higher-current-week-order-volume product line gets the slot. Others stay overdue.
  4. Every other weekend (designated maintenance weekend, ~26/year): repeat
     steps 2-3 once more for a second chance. PM done here costs ZERO scheduled
     operating hours (weekends were never scheduled production time) -- no
     Availability impact, unlike weekday PM.
```

At most one PM job per week (weekday) plant-wide, plus at most one more on designated maintenance weekends — never two machines serviced in the same week, and never guaranteed that a given machine's turn actually comes on its 30-day due date.

| Event | Duration | Restoration |
|---|---|---|
| PM | Uniform(1, 3) hours (weekday); 0 scheduled hours if performed on a designated maintenance weekend | All 3 sensors reset to `H_s = Uniform(0.90, 0.95)` |
| Breakdown | Uniform(2, 8) hours | Primary sensor (§3) → `Uniform(0.90, 0.95)`; sensors with sensitivity > 0.3 (but not primary) → `Uniform(0.70, 0.80)`; sensors with sensitivity ≤ 0.3 → unchanged (not touched by this repair) |

Either event: log to CMMS, draw a new `mode` and `T_fail` for the next cycle, reset `t = 0`. A machine whose PM keeps losing the weekly/weekend contest simply keeps accruing wear on its current cycle — `t` keeps advancing past what a 30-day cadence would have allowed, exactly the mechanism intended.

**Technician notes**: 3-4 template strings per mode (e.g., bearing wear → *"Vibration trending up over past week, elevated bearing temp; bearing replaced."*), randomly selected per event — deterministic templates, no LLM call needed at generation time.

## 6. Right-censoring (FR-DG-11)

Whatever cycle is in progress — for **either** reason — is right-censored, not a third category:

- **Historical window boundary**: a cycle still running when the 3-year-minus-30-day window ends.
- **PM preempting a breakdown**: a cycle ended by scheduled PM before `T_fail` was reached.

Both cases get the same label: `hours_survived_so_far` = operating hours from cycle start to the stopping point, `y_upper = +inf`, no failure time recorded — we only know the machine survived at least that long, not what its (unobserved, internal-to-the-simulator) `T_fail` would have been. Only cycles that actually reach `T_fail` before any PM produce a genuine uncensored failure observation. This falls out of the simulation mechanics in §4-§5 by construction; the labeling logic just needs to check *why* each cycle ended, not only whether it's the last one in the window.

## 7. Orders (root input) & derived utilization (FR-DG-07, FR-DG-08, FR-DG-01b)

**Causality runs order → utilization → wear, not the reverse**: CoEVheeler/CoCoCars place firm EDI 862 orders → SnowComotive schedules production to fulfill them → the schedule is what feeds §4's wear simulation. Orders are the independent input; utilization is derived.

**Orders — one continuous generated series, full 3-year history + 8-week look-ahead:**

```
-- EV Brake Caliper: mild linear trend across the 3-year history, then a two-beat
--   look-ahead structure (not a single spike) for the demo's priority-flip moment
order_units_week = baseline_ev_caliper * (1 + 0.20 * weeks_elapsed / 156) * lookahead_ramp + noise
   -- for historical weeks (weeks_elapsed <= 156): lookahead_ramp = 1.0

lookahead_ramp (weeks 157-160, look-ahead weeks 1-4):
  ramps gradually 1.0 -> 1.6 across these 4 weeks (linear interpolation, not a step)
lookahead_ramp (weeks 161-164, look-ahead weeks 5-8):
  holds at 1.6 -- Caliper demand stays elevated through the second half too

-- ICE Engine Head: mild linear decline across history, THEN a two-beat look-ahead
--   that deliberately diverges from Caliper's timing
order_units_week = baseline_ice_headfoo * (1 - 0.15 * weeks_elapsed / 156) * lookahead_bump + noise
   -- for historical weeks: lookahead_bump = 1.0 (pure decline continues)

lookahead_bump (weeks 157-160, look-ahead weeks 1-4):
  stays at 1.0 -- flat, no pickup yet; this is why the crew prioritizes Caliper
  during this window (FR-DG-05a's demand-based tie-break)
lookahead_bump (weeks 161-164, look-ahead weeks 5-8):
  ramps gradually 1.0 -> 1.3 across these 4 weeks -- a renewed uptick, breaking
  the decline trend, giving Engine Head its own demand-driven urgency just as
  its deferred maintenance (accumulated during weeks 1-4) becomes pressing too

-- ICE Caliper, EV Engine Head (secondary variants, low volume): flat baseline + noise

noise ~ Normal(0, 0.05 * baseline)              -- ±5% weekly noise, all series
```

Both ramps are gradual (linear interpolation across their 4-week beat), not instant steps — firm orders building up over a few weeks reads more like genuine incoming EDI 862 commitments than an unexplained vertical jump. Lands as a normal Raw source (Parquet → Stage → `COPY INTO`), same as everything else — no dbt derivation.

**Utilization — derived from orders, inside the generator's simulation loop (not a table):**

```
required_hours_week(product) = smoothed_orders_week(product) / throughput_units_per_hour
  -- smoothed_orders = trailing 4-week moving average, so the schedule responds to a
  --   sustained shift, not one week's random order noise

available_hours_week = working_days_this_week * 24 - downtime_hours_this_week(PM/breakdown, §5)

operating_hours_week = min(required_hours_week, available_hours_week)
  -- if required > available: capacity-capped, no overtime modeled for MVP;
  --   the shortfall is unfulfilled demand (consistent with, not separately tracked
  --   beyond, the existing $-at-risk Impact Statement formula)
```

Sequential value-stream stages (CNC Boring → CNC Milling, both Caliper line) receive the **same** `required_hours_week` — each stage processes the same batch, this isn't split/summed across them. `operating_hours_week` is then allocated across that week's working days and fed tick-by-tick into §4's wear simulation as `t` increments.

**Utilization consequence (not the source of demo tension — that's §5's crew capacity)**: because Caliper's orders trend up and Engine Head's trend down over the 3 years, Caliper machines organically log somewhat more operating hours in recent periods while Engine Head logs somewhat fewer. Per-hour wear rate itself stays neutral by design (§4's Weibull parameters don't differ by machine for this reason) — the actual counter-intuitive story comes from §5's maintenance crew capacity constraint (Caliper serviced on schedule but re-wears fast; Engine Head's PM keeps losing the priority contest during weeks 1-4 of the look-ahead specifically, per this section's `lookahead_bump` staying flat then), not from Engine Head having a worse wear-rate.

**Inventory**: finished-goods stays close to a target days-of-supply level historically (production tracks orders closely by construction, absent a breakdown-driven shortfall); tightens (lower target) during the look-ahead's EV spike window to make the inventory-buffer factor in the priority score (HLD §5) bite during the demo. Spare parts: decrement by 1 per repair event consuming that part (§5); replenish after `lead_time_days` (Module 1's `STD.SPARE_PART_SNAPSHOT.lead_time_days`).

## 8. Historical/live split & volume

The generator runs one integrated chronological loop (§9) producing sensor ticks, CMMS events, *and* consuming the already-generated order series together — not three independent passes. Only **sensor ticks** get the 30-day drip-feed treatment: hold back the trailing 30 days as individual pre-generated Parquet micro-batches (one per tick, per FR-PL-04b) rather than bulk-loading them. Orders/inventory (weekly grain) don't need this — they're simply generated and landed normally across the full 3yr+8wk timeline (FR-DG-10). Sensor volume matches the earlier back-of-envelope: 3 machines × 3 sensors × 96 reads/day × ~694 operating days ≈ 600K historical rows; ~18K rows in the 30-day live-release window (HLD §"Orchestration & Scheduling" cross-check).

## 9. Generation algorithm (outline)

1. Build calendar (§1) and the full order series (§7) — both needed before the main loop, since utilization depends on orders.
2. Run **one week-major loop** (not per-machine) from 3 years ago to "now" + into the 8-week look-ahead — the crew capacity constraint (§5) is shared across all 3 machines within a week, so machines can't be processed independently end-to-end:
   a. Draw this week's crew-capacity outcome (§5: breakdown check, background plant draw, then priority contest among machines with PM due) — this determines which machine, if any, gets serviced this week.
   b. For each of the 3 machines, look up this week's orders for its product (§7), derive `required_hours_week`, cap at `available_hours_week` (net of any downtime from step a's outcome for that specific machine).
   c. For each machine, allocate `operating_hours_week` across working days; generate a sensor tick every 15 minutes during those hours, applying §4's health/reading formula (`t` increments by real operating hours).
   d. Each tick: check for `T_fail` reached (§4) — if so, immediate breakdown (bypasses the weekly crew contest, per §5), log the CMMS event, apply restoration, draw a new failure mode + `T_fail`, reset `t = 0`. PM restoration (if this machine won the week's/weekend's crew slot per step a) applies similarly.
3. Note: sensor generation stops at "now" — the 8-week look-ahead only has orders/inventory, no simulated sensor ticks (RUL is a model prediction from current state, not a simulation of future readings; BRD assumption 12). The crew-capacity loop (step 2a) still runs through the look-ahead, though — PM contention and neglect continue to accrue in that window even without sensor ticks, since it's needed to know each machine's `hours_since_last_service` at "now" and how the look-ahead's own contention plays out for the demo narrative.
4. Generate equipment master and calendar tables (§2, §1).
5. Split sensor output at the 30-day boundary: bulk historical → Parquet for immediate load; trailing 30 days → per-tick Parquet files held for progressive release (FR-PL-04b). Orders/inventory land normally, no split.
6. Write everything as Parquet to the Snowflake Stage (FR-DG-12) — no CSV, no direct table writes.

## 10. Fallback: manual override if the simulation doesn't land the narrative

§5's crew-capacity mechanism is stochastic (Bernoulli background-plant draw, priority contest, Weibull failure timing) — it is the intended, causally-honest way to produce Engine Head's "overdue and at-risk" state by demo day, but a single generation run on a given seed is not *guaranteed* to land it convincingly (e.g., Engine Head could win enough of the weekly/weekend contests that it isn't meaningfully overdue when "now" arrives, or its accumulated wear isn't visually dramatic enough).

**Accepted fallback, decided up front rather than discovered under deadline pressure**: if, after generation, the trailing-30-day window doesn't show a sufficiently overdue/at-risk Engine Head, do **not** iterate on RNG seeds indefinitely or bend the simulation logic (§5-7) to special-case the outcome. Instead, directly hand-patch the generated trailing-30-day data for Engine Head after generation completes:

- Push `CONS.FCT_MAINTENANCE_EVENT`'s last PM record for CNC Horizontal further back in time (increasing `hours_since_last_service` at "now").
- Adjust the corresponding trailing-30-day `RAW.SENSOR_READING` rows for CNC Horizontal to reflect the additional unattended wear that longer gap implies (re-apply §4's health/reading formula with a larger `t`, rather than freehand edits — keeps the patched data internally consistent with the same degradation curve the model was trained on).

This is a one-time, explicit, documented **post-generation data patch** on the output — not a change to the generation algorithm, and not a reversion of the causal design (§5-9 remain the primary path and should be the first thing attempted on a re-roll or two). It's a pragmatic override accepted for demo reliability, given the mechanism's inherent randomness, and should be called out plainly if it's used (e.g., a one-line note in the demo script or README — "trailing-30-day Engine Head maintenance data was hand-adjusted post-generation to ensure the priority-flip narrative; underlying generation logic is unchanged"). Cross-referenced from BRD assumption 15 and FRD FR-DG-05a.

## Known simplifications (BRD assumptions 9-10, 12-15)

- **No overtime modeled** — if a week's required hours (from orders) exceed available capacity, the excess is simply unfulfilled, capped at capacity rather than scheduling overtime/extra shifts.
- **No cold-start/warm-up transient** after idle periods — §4's health formula correctly doesn't reset the long-term wear curve on idle time, but also doesn't model the separate short-term effect of a machine starting at a more optimal reading and ramping up over its first ~15-60 minutes running. Noted as a future improvement, not built for MVP.
- **RUL never requires simulating future sensor data** — the model predicts "hours from now" from currently-available features; the 8-week look-ahead only carries orders/inventory, never simulated sensor ticks.
- **The plant's other, non-instrumented machines are a background probability draw, not a real simulation** (§5, BRD assumption 14) — keeps scope to the 3 monitored machines while still representing that they aren't the only claim on crew attention.
