# LLD Module 3 — Standardization & Consumption Build
## SnowComotive — Predictive Maintenance & Overall Equipment Effectiveness (OEE) Command Center

Status: Draft v0.1

This module gives the executable SQL behind `STD.SENSOR_READING`'s leakage-safe joins and `CONS.FCT_SENSOR_READING`'s pass-through. **This is data pre-processing (cleaning + lean dim/fact build), not ML feature engineering** — it produces a general-purpose atomic Consumption fact, in real physical units, that any consumer (dashboard, semantic view, agent) can read directly. Rolling-window aggregation, normalization, and all training/inference feature preparation are a distinct, model-specific concern handled entirely in `FEAST` (Module 4) — not here.

---

## 1. Standardized: leakage-safe joins (FR-PL-02, FR-PL-03)

`STD.SENSOR_READING` adds two columns to the Raw grain (same row count, no aggregation) — both are elapsed-time-since-an-event joins, resolved the same way:

- `hours_since_last_service` — the most recent maintenance event that **completed strictly before** this reading's timestamp.
- `hours_since_install` — elapsed time since the machine's `commissioned_ts` (Module 1) — the equipment's own "birth" event, always exactly one row per machine, never updated.

Both are leakage-safety-relevant: using the wrong (later, in-progress, or same-timestamp) service event, or ignoring installation age entirely, would let a model see information that, chronologically, wasn't yet available or would omit a genuinely predictive signal (older equipment general wear-and-tear, independent of the current maintenance cycle).

```sql
-- STD.SENSOR_READING (dynamic_table, target_lag = 15 minutes)
SELECT
    r.reading_id,
    r.equipment_id,
    r.reading_ts,
    r.sensor_type,
    r.reading_value,
    DATEDIFF('hour', m.event_end_ts, r.reading_ts)         AS hours_since_last_service,
    DATEDIFF('hour', e.commissioned_ts, r.reading_ts)      AS hours_since_install
FROM raw.sensor_reading r
JOIN raw.equipment e
    ON e.equipment_id = r.equipment_id
LEFT ASOF JOIN raw.cmms_log m
    MATCH_CONDITION (r.reading_ts > m.event_end_ts)   -- strictly greater-than = strictly less-than the other way (FR-PL-03)
    ON r.equipment_id = m.equipment_id
```

Uses Snowflake's native **`ASOF JOIN`** (`MATCH_CONDITION`) for `hours_since_last_service` rather than a correlated subquery or `QUALIFY ROW_NUMBER()` self-join — it's built exactly for "find the single most recent row in another table relative to this row's timestamp." `LEFT ASOF JOIN` null-pads a machine with no prior service (its very first cycle after commissioning) rather than dropping the row — `hours_since_install` covers that gap for such rows, since it's always populated.

**No calendar join.** An earlier draft joined `RAW.CALENDAR` here to derive an `is_working_period` flag. Removed: the data generator (Module 2, FR-DG-04) never emits a sensor tick for non-operating time in the first place — every row already reaching Standardized is, by construction, a working-period reading. A calendar join to re-derive a flag that's always `TRUE` is dead weight (extra join cost, zero information). If a future iteration changes the generator to emit idle-state ticks (matching how real SCADA sensors report continuously regardless of production state), this flag would need to be reintroduced at that time — noted, not built now.

## 2. Consumption: lean pass-through (FR-PL-05)

`CONS.FCT_SENSOR_READING` is a straight pass-through of `STD.SENSOR_READING` — no aggregation, no rolling windows, no normalization. This is deliberately lean:

```sql
-- CONS.FCT_SENSOR_READING (dynamic_table, target_lag = 15 minutes)
SELECT equipment_id, reading_ts, sensor_type, reading_value,
       hours_since_last_service, hours_since_install
FROM std.sensor_reading
```

Rolling 1h/8h/24h/7d averages and baseline normalization — which an earlier draft materialized directly in this fact — have moved entirely to `FEAST.FCT_SENSOR_FEATURES_INFERENCE`/`FEAST.FCT_SENSOR_FEATURES_TRAIN` (Module 4), computed via a shared macro. The reasoning: this fact should stay the single, general-purpose atomic grain that the dashboard, semantic view, and agent all read in real units — rolling/normalized values are a model-serving concern with their own reuse and correctness requirements (§3 below), and belong in a layer whose only consumers are training and inference.

## 3. Correctness invariant carried into FEAST: backward-only windows

This module no longer computes rolling windows itself, but the invariant that makes them safe to compute incrementally in `FEAST` (Module 4) depends on properties established here, so it's documented at this boundary:

- `CONS.FCT_SENSOR_READING`'s ticks are strictly ordered and append-only per `(equipment_id, sensor_type)` — a new tick never rewrites or invalidates an earlier one.
- Any rolling-window feature computed **backward-looking only** (`ROWS BETWEEN N PRECEDING AND CURRENT ROW`, ordered by `reading_ts`) therefore has a critical property: a new tick's arrival changes *only that new tick's* output row. Every earlier row's rolling average was computed from rows at-or-before itself and is never touched again.
- This is what makes it safe for `FEAST.FCT_SENSOR_FEATURES_INFERENCE` to feed `MODEL(...)!predict(...)` on a 15-minute incremental cadence without re-scoring history: if the feature table's old rows never change, the downstream prediction dynamic table has no reason to touch them either — only the new feature row is new input, so only one new prediction row is produced per tick. This is also what FR-FS-06's alert-smoothing logic (N-of-M consecutive high-risk evaluations) implicitly depends on — a past high-risk flag must not retroactively flicker because a later tick arrived.
- Same-batch ordering is handled for free: if two new ticks land in the same 15-minute refresh (a catch-up scenario), the second tick's window correctly includes the first as a preceding row, because the window function operates over true row order (`ORDER BY reading_ts`), not "this refresh's batch."

**What this does *not* guarantee, and must be verified at build time**: whether Snowflake's dynamic table engine actually recognizes this backward-only shape as incrementally maintainable, or falls back to a full-table rescore on every refresh despite the values being unchanged. If it silently falls back to full recompute, the *engine* may still internally rewrite every row's storage on each refresh — and if that causes the downstream model-inference dynamic table to see the entire source as "changed" and re-run `predict()` on all historical rows rather than just the new one, that's a real correctness/cost problem (re-scoring history is wasted compute, and if the model itself is non-deterministic in any way, could even change historical predictions). This is escalated from Module 4's original "performance verification" framing to an explicit **correctness invariant to confirm empirically before trusting the 15-minute cadence in the demo** — not just a cost optimization.
