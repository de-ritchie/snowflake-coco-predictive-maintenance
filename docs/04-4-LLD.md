# LLD Module 4 — Feature Engineering (FEAST: dbt-native feature store)
## SnowComotive — Predictive Maintenance & Overall Equipment Effectiveness (OEE) Command Center

Status: Draft v0.1
Traces to: [02-FRD.md](02-FRD.md) Section D (FR-FS-00 through FR-FS-08, FR-FS-09) | [04-3-LLD.md](04-3-LLD.md)

**No external Feature Store SDK is used** (no `Entity`, `FeatureView`, `generate_training_set`). Feature engineering is reciprocated entirely inside dbt as a new `FEAST` schema — one macro implementing the transformation logic once, invoked from two dbt models that differ only in materialization (always-fresh vs. frozen-per-training-run). This keeps the whole pipeline (Raw → Standardized → Consumption → FEAST → model) in one tool's DAG, testing framework, and lineage — no separate Python object graph to keep in sync.

---

## 1. The macro: `sensor_rolling_features(source_relation)`

One dbt macro implements rolling-window computation and baseline normalization, **then pivots from long format (one row per sensor type) to wide format (one row per tick, one column per sensor type)** — this is what makes the output genuinely usable as joint/multivariate input for IsolationForest (FR-FS-00 requires vibration+temperature+RPM seen together per tick, not as three independent single-sensor rows). Parameterized only by which relation to read from:

```sql
{% macro sensor_rolling_features(source_relation) %}
WITH normalized AS (
    SELECT
        s.equipment_id,
        s.reading_ts,
        s.sensor_type,
        (s.reading_value - b.baseline_mean) / b.baseline_std AS reading_value_z,
        (AVG(s.reading_value) OVER (
            PARTITION BY s.equipment_id, s.sensor_type ORDER BY s.reading_ts
            ROWS BETWEEN 3 PRECEDING AND CURRENT ROW            -- 1h = 4 ticks
        ) - b.baseline_mean) / b.baseline_std                    AS rolling_1h_avg_z,
        (AVG(s.reading_value) OVER (
            PARTITION BY s.equipment_id, s.sensor_type ORDER BY s.reading_ts
            ROWS BETWEEN 31 PRECEDING AND CURRENT ROW           -- 8h = 32 ticks
        ) - b.baseline_mean) / b.baseline_std                    AS rolling_8h_avg_z,
        (AVG(s.reading_value) OVER (
            PARTITION BY s.equipment_id, s.sensor_type ORDER BY s.reading_ts
            ROWS BETWEEN 95 PRECEDING AND CURRENT ROW           -- 24h = 96 ticks
        ) - b.baseline_mean) / b.baseline_std                    AS rolling_24h_avg_z,
        (AVG(s.reading_value) OVER (
            PARTITION BY s.equipment_id, s.sensor_type ORDER BY s.reading_ts
            ROWS BETWEEN 671 PRECEDING AND CURRENT ROW          -- 7d = 672 ticks
        ) - b.baseline_mean) / b.baseline_std                    AS rolling_7d_avg_z,
        s.hours_since_last_service,
        s.hours_since_install
    FROM {{ source_relation }} s
    JOIN cons.dim_sensor_baseline b
        ON b.equipment_id = s.equipment_id AND b.sensor_type = s.sensor_type
)
SELECT
    equipment_id,
    reading_ts,
    MAX(CASE WHEN sensor_type = 'vibration'   THEN reading_value_z    END) AS vibration_z,
    MAX(CASE WHEN sensor_type = 'vibration'   THEN rolling_1h_avg_z   END) AS vibration_rolling_1h_z,
    MAX(CASE WHEN sensor_type = 'vibration'   THEN rolling_8h_avg_z   END) AS vibration_rolling_8h_z,
    MAX(CASE WHEN sensor_type = 'vibration'   THEN rolling_24h_avg_z  END) AS vibration_rolling_24h_z,
    MAX(CASE WHEN sensor_type = 'vibration'   THEN rolling_7d_avg_z   END) AS vibration_rolling_7d_z,
    MAX(CASE WHEN sensor_type = 'temperature' THEN reading_value_z    END) AS temperature_z,
    MAX(CASE WHEN sensor_type = 'temperature' THEN rolling_1h_avg_z   END) AS temperature_rolling_1h_z,
    MAX(CASE WHEN sensor_type = 'temperature' THEN rolling_8h_avg_z   END) AS temperature_rolling_8h_z,
    MAX(CASE WHEN sensor_type = 'temperature' THEN rolling_24h_avg_z  END) AS temperature_rolling_24h_z,
    MAX(CASE WHEN sensor_type = 'temperature' THEN rolling_7d_avg_z   END) AS temperature_rolling_7d_z,
    MAX(CASE WHEN sensor_type = 'rpm'          THEN reading_value_z    END) AS rpm_z,
    MAX(CASE WHEN sensor_type = 'rpm'          THEN rolling_1h_avg_z   END) AS rpm_rolling_1h_z,
    MAX(CASE WHEN sensor_type = 'rpm'          THEN rolling_8h_avg_z   END) AS rpm_rolling_8h_z,
    MAX(CASE WHEN sensor_type = 'rpm'          THEN rolling_24h_avg_z  END) AS rpm_rolling_24h_z,
    MAX(CASE WHEN sensor_type = 'rpm'          THEN rolling_7d_avg_z   END) AS rpm_rolling_7d_z,
    MAX(hours_since_last_service) AS hours_since_last_service,   -- identical across all 3 sensor_type rows for a given tick
    MAX(hours_since_install)      AS hours_since_install
FROM normalized
GROUP BY equipment_id, reading_ts
{% endmacro %}
```

**Assumption this pivot relies on**: all 3 sensors for a given machine share the exact same `reading_ts` at each 15-minute tick (Module 2 §9c generates one tick per machine per interval, producing 3 rows — one per sensor type — with identical timestamps). If a future generator change ever let sensors drift out of lockstep, the `GROUP BY equipment_id, reading_ts` would silently split what should be one tick into partial rows (`NULL` for whichever sensor didn't share that exact timestamp) — worth a data-quality test (FR-PL-08) checking that every tick has exactly 3 sensor rows before this macro runs, not just trusting it.

Tick-to-hour conversion (15-min cadence, FR-DG-01a): 1h=3, 8h=31, 24h=95, 7d=671 preceding rows — unchanged from the earlier Module 3 draft, just relocated here. Cold-start behavior (short partitions average over however many rows exist) is unchanged too.

**Correctness invariant (Module 3 §3, restated here since this is where it matters operationally)**: every window above is backward-looking only, so a new tick never rewrites an earlier tick's output — this is what makes `FCT_SENSOR_FEATURES_INFERENCE`'s incremental refresh (§2) safe to trust. The pivot (`GROUP BY equipment_id, reading_ts`) doesn't change this: it's a reshape of the same per-sensor computation, still keyed on the same immutable `reading_ts`. This must still be empirically confirmed at build time, not assumed.

## 2. Two invocations, two materializations

```sql
-- FEAST.FCT_SENSOR_FEATURES_INFERENCE (dynamic_table, target_lag = 15 minutes)
{{ sensor_rolling_features(source_relation=ref('fct_sensor_reading')) }}
```

```sql
-- FEAST.FCT_SENSOR_FEATURES_TRAIN (table, rebuilt at each training run — FR-OPS-02a)
{{ sensor_rolling_features(source_relation=ref('fct_sensor_reading')) }}
```

Identical SQL, different `materialized` config in each model's `.yml`/config block. This is the actual reuse benefit: **one** transformation definition, not two copies to keep in sync by hand. They're materialized twice, not queried once, for a specific reason: training must run against a **frozen** snapshot. If training queried the live dynamic table directly (with a `WHERE reading_ts <= cutoff` filter) while that same table kept incrementally refreshing in the background during a multi-minute training job, the run wouldn't be strictly reproducible — a re-run five minutes later could see additional rows even for the same nominal cutoff, if refresh timing and query timing interleave unpredictably. `FCT_SENSOR_FEATURES_TRAIN` fixes that: it's rebuilt once, explicitly, as its own pipeline step (FR-OPS-02a), and doesn't change again until the next deliberate rebuild.

`FCT_SENSOR_FEATURES_INFERENCE` is what `cons.fct_anomaly_result` and `cons.fct_rul_prediction` (Module 1) read `FROM` in their `MODEL(...)!predict(...)` calls — replacing the earlier design's direct read of `cons.fct_sensor_reading`.

## 3. Predicting only new events, not re-deriving history (critical correctness property)

A specific risk worth naming explicitly: **rolling features need history as input (up to 7 days of prior ticks), but that must not mean re-predicting on historical rows every time a new tick arrives.** The two are separable because of §1's backward-only invariant:

- Computing a new tick's `rolling_7d_avg_z` **reads** up to 671 prior rows — necessary, unavoidable, that's what a rolling average is.
- But it **writes** exactly one new output row. No prior row's already-computed feature values change, because their own windows never looked forward past themselves.
- Therefore `FCT_SENSOR_FEATURES_INFERENCE`'s dynamic table has exactly one genuinely new row per tick per `equipment_id` (one row now, post-pivot §1 — not per sensor type) to offer downstream — and `cons.fct_anomaly_result`/`fct_rul_prediction`, refreshing incrementally off that one new row, correctly predicts *only* on the new event, never re-scoring the history it happened to read through to compute that one row's rolling context.
- This holds regardless of how much or how little history exists yet for a given machine: a brand-new machine's very first tick still only produces one output row (with short/degenerate windows per the cold-start note in §1) — it never "catches up" by re-emitting predictions for ticks that don't exist.
- The one thing that would break this is exactly Module 3 §3's open verification item: if the dynamic table engine falls back to a full rescore (rewriting every row's *storage*, even though the *values* are identical) rather than a true incremental append, a naively-implemented downstream consumer could misinterpret "every row touched by this refresh" as "every row is new" and re-run `predict()` on all of history. Confirming true incremental refresh (not just functional correctness) is therefore the single most safety-critical build-time verification in this design — elevated here for a third time (Module 3 §3, Module 1's Deferred section, and here) because it's easy to under-weight as "just a cost thing."

## 4. Training spine and datasets

### 4a. RUL (survival) spine — per maintenance cycle

```sql
-- FEAST.SPINE_MAINTENANCE_CYCLE (table, training-only — moved here from Consumption, Module 1)
SELECT
    equipment_id,
    cycle_end_ts,
    hours_survived_so_far AS y_lower,
    CASE WHEN is_censored THEN NULL ELSE hours_survived_so_far END AS y_upper
FROM cons.fct_maintenance_event   -- derived: consecutive event pairs per machine, or window-end for the still-open final cycle
```

```sql
-- FEAST.TRAINING_DATASET_RUL (table)
-- feat is already one row per (equipment_id, reading_ts) post-pivot (§1) — no per-sensor-type fanout to worry about
SELECT
    spine.equipment_id, spine.cycle_end_ts, spine.y_lower, spine.y_upper,
    feat.* EXCLUDE (equipment_id, reading_ts),
    CASE WHEN spine.cycle_end_ts <= DATEADD('month', -6, CURRENT_DATE() - 30)
         THEN 'train' ELSE 'test' END AS dataset_split          -- FR-FS-03: time-based, not random
FROM feast.spine_maintenance_cycle spine
LEFT ASOF JOIN feast.fct_sensor_features_train feat
    MATCH_CONDITION (spine.cycle_end_ts >= feat.reading_ts)
    ON spine.equipment_id = feat.equipment_id
```

### 4b. IsolationForest — per tick, unsupervised

```sql
-- FEAST.TRAINING_DATASET_ISO (table)
SELECT *,
    CASE WHEN reading_ts <= DATEADD('month', -6, CURRENT_DATE() - 30)
         THEN 'train' ELSE 'test' END AS dataset_split
FROM feast.fct_sensor_features_train
```

No spine or ASOF join needed here — the label-free training set is just the frozen feature snapshot itself with a split flag.

---

## 5. Inference reads FEAST, bypasses everything else in this module

Inference (`cons.fct_anomaly_result`, `cons.fct_rul_prediction`) needs none of §4's spine/split machinery — it only ever wants "the current feature row for this machine," which `FCT_SENSOR_FEATURES_INFERENCE` already provides via a plain `FROM` clause inside the model-inference dynamic table's `SELECT`. This asymmetry (training goes through spine+split, inference doesn't) is intentional, not an inconsistency: training needs point-in-time-correct historical examples with labels; inference needs only the latest state, which is already what a dynamic table naturally holds.
