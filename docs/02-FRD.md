## 0. Purpose

This FRD translates the BRD's scope and demo narrative into functional requirements per module, and formally defines the **Systems Landscape** (which BRD deferred here). It does not define table schemas, model hyperparameters, or agent prompt text — those are HLD/LLD.

Modules: (A) Systems Landscape, (B) Synthetic Data Generation, (C) Data Pipeline (dbt / Raw-Standardized-Consumption / Dynamic Tables), (D) Feature Engineering & Model, (E) Semantic Layer & Agents, (F) Command Center (Streamlit), (G) Jira Integration, (H) SDLC Tooling (custom CoCo agents), (I) Environment & Operations.

**Naming note:** this project does not use "Bronze/Silver/Gold" medallion terminology. Layers are named **Raw** (unmodified copy of source, no cleaning/joining/aggregation), **Standardized** (cleaned, typed, joined/conformed — same grain as source, never aggregated), and **Consumption** (dimension/fact tables, aggregates, feature tables, marts).

## A. Systems Landscape / Source System Register

| # | Data domain | Real-world source system | MVP representation | Cadence (real) | Cadence (MVP) | Landing zone |
|---|---|---|---|---|---|---|
| A1 | Equipment master, line/machine routing, throughput rates | MES / EAM (e.g. SAP PM) | Snowpark generator → Parquet → Stage | Rarely changes | Static | Stage (Parquet) → Raw table via `COPY INTO` |
| A2 | Historical sensor telemetry (3yr → 30d ago) | SCADA / IoT historian (e.g. OSIsoft PI) | Snowpark synthetic generator script → Parquet → Stage | Sub-second/continuous | Uniform 15-min cadence (locked — see FR-DG-01a) | Stage (Parquet) → Raw table via `COPY INTO` |
| A3 | Recent sensor telemetry (last 30 days) | Same historian, live feed | Scheduled task appends Parquet micro-batches to Stage | Sub-second/continuous | Every 15 min (or manual trigger for demo) | Stage → Raw landing table → Dynamic Table (target_lag = 15 min) |
| A4 | CMMS maintenance logs (PM + breakdown + repair notes + technician free-text notes as a column) | CMMS (e.g. IBM Maximo / SAP PM) | Synthetic generator, tied to A2/A3 decay events → Parquet → Stage | Event-driven | Static (historical), append-only going forward | Stage (Parquet) → Raw table via `COPY INTO` |
| A5 | New maintenance/incident tickets (going forward only) | Jira Service Management | Agent-created via Jira REST API / MCP — **write path only, never imported** | Event-driven | Event-driven (agent tool call) | External (Jira), referenced by ID in Snowflake |
| A6 | Firm sales orders (near-term) | ERP (SAP SD), fed by EDI 862 Shipping Schedule from OEM | Synthetic weekly order-volume generator → Parquet → Stage — root/independent input, spans full 3yr history + 8wk look-ahead as one continuous series | Weekly (typical EDI 862 cadence) | Weekly | Stage (Parquet) → Raw table via `COPY INTO` |
| A7 | Inventory (finished goods + spare parts) | ERP/WMS | Synthetic weekly snapshot generator → Parquet → Stage | Weekly/daily | Weekly | Stage (Parquet) → Raw table via `COPY INTO` |
| A8 | Working/holiday calendar | HR / plant calendar system | Synthetic calendar dimension generator → Parquet → Stage | Static/annual | Static | Stage (Parquet) → Raw table via `COPY INTO` |
| A9 | Model outputs (anomaly detection results, RUL predictions) | N/A (internal, produced by D) | Consumption-layer dynamic tables calling the registered model directly in SQL (`MODEL(model_name, version)!predict(...)`, FR-FS-00b) — no stored procedure, no Task | N/A | Continuous, 15-min `target_lag`, driven by the upstream sensor tick refresh | Computed directly as Consumption fact tables (`cons.fct_anomaly_result`, `cons.fct_rul_prediction`) — no Raw/Standardized re-entry (FR-PL-06 superseded) |
| A10 | Dev/project tracking | N/A (net-new for this project) | Jira Kanban board (Epics/Stories/Tasks) | N/A | Manual, per-story | External (Jira), not part of the data pipeline |

**Explicit notes:**
- A5 and A10 are both Jira, but different projects (A5 = Service Management project for plant incidents; A10 = Kanban project for this build's own SDLC). Do not conflate.
- No standalone unstructured-document source in MVP scope — maintenance manual/technician-note content is captured as a text column on A4, not separate files. Document parsing (AI_PARSE_DOCUMENT) is a future/stretch extension only, not core scope.
- All structured sources land as **Parquet in a Snowflake Stage**, then `COPY INTO` a Raw table — dbt does not perform the initial load (dbt seeds are CSV-only and not used here); dbt owns only Raw → Standardized → Consumption transformation.
- A9 (model outputs) is the one exception to the Raw→Standardized→Consumption load path: it never has a Raw table, because inference itself runs as a Consumption-layer dbt model (FR-FS-00b) — there is no external system boundary to land across.

## B. Synthetic Data Generation — Functional Requirements

| ID | Requirement |
|---|---|
| FR-DG-01 | Generate a calendar dimension covering 3 years ago → current date + forecast horizon, flagging working day, holiday, and shift (3×8hr) for a 5-day work week. |
| FR-DG-01a | **Sensor data cadence is locked at a uniform 15 minutes** for both historical generation and live injection (not per-second, not per-minute) — matches the Dynamic Table refresh cadence (FR-PL-04) and keeps total volume in the low hundreds-of-thousands of rows (BRD back-of-envelope), managing Snowflake credit usage on a trial account. |
| FR-DG-01b | Machine operating hours per week are **derived from orders** (FR-DG-07), not an independent idle-rate trend: required_hours = smoothed(orders) / throughput, capped at available capacity (working days × 24 operating hours, no overtime modeled). This is computed inside the generator's simulation loop — it is not a table, not a dbt model, purely an internal input to FR-DG-04's wear simulation. A small residual idle chance (~2-3%/working day), independent of orders, still applies on top (BRD assumption 9). Sequential value-stream stages (CNC Boring → CNC Milling on the Caliper line) receive the *same* required-hours number, not a split — each stage processes the same batch. |
| FR-DG-02 | Generate equipment master data for all value-stream stages (BRD §5.1), marking exactly 3 machines as sensor-enabled: CNC Boring, CNC Milling (Caliper line), CNC Horizontal Machining Center (Engine Head line). Each machine has machine-specific baseline sensor parameters (distinct mean/variance per sensor per machine — no shared baseline across machine types). |
| FR-DG-03 | For each sensor-enabled machine, generate 4-5 canonical failure-mode signatures with distinct signal behavior: (a) bearing wear — vibration + temperature trend together over weeks; (b) tool/insert wear — vibration spikes only, temp/RPM stable; (c) coolant/thermal degradation — temperature trend only; (d) servo/RPM instability — RPM trend only, vibration/temp largely stable; (e) unexplainable stoppage — no sensor precursor, ~10-15% of all breakdowns for that machine. |
| FR-DG-04 | Model per-sensor health as a decaying quantity (Weibull-shaped degradation) plus random noise, evaluated only during actual operating hours — determined by FR-DG-01b's order-derived weekly schedule, not a fixed calendar allocation. No decay accrues during holidays/non-working periods or capacity-shortfall gaps; a small residual unplanned idle chance (~2-3% per working day, FR-DG-01b) must also be generated, independent of orders (machine scheduled but not running, no explainable cause). |
| FR-DG-05 | On a maintenance event (PM or breakdown repair), restore affected sensor health to 70-95% of full baseline, not 100%. PM events recover a broader set of sensors on the machine at the higher end of the range; breakdown repairs recover primarily the failed component's sensor signal, with partial or no recovery on co-located sensors. *When* a PM event actually happens is governed by FR-DG-05a's crew-capacity constraint, not simply "every 30 days per machine." |
| FR-DG-05a | **Maintenance crew capacity (plant-wide, shared, limited)**: at most 1 weekday PM job per week across all machines (sensor-enabled and not), plus 1 additional job on designated maintenance weekends (biweekly, ~26/year — zero Availability impact since weekends aren't scheduled production time). Each week/weekend slot has a background ~20-30% chance of already being consumed by an unrelated, non-instrumented part of the plant (Casting, Drilling, Deburr, Coating, Assembly, etc. — not separately simulated, just a probability draw standing in for their existence). If the slot is free and multiple monitored machines are due, priority goes to whichever product line has higher current-week order volume (FR-DG-07) — the other(s) remain overdue. Breakdowns bypass this cap entirely — always immediate, any day. This is the mechanism behind BRD assumption 15 (why Engine Head can go unattended longer despite a moderate wear rate). **Fallback**: since this is a stochastic mechanism, it is not guaranteed to land the intended outcome on every run — if it doesn't, LLD Module 2 §10 defines an accepted post-generation hand-patch of Engine Head's trailing-30-day data rather than reworking the simulation logic. |
| FR-DG-06 | Generate CMMS maintenance log entries co-incident with every PM and breakdown event from FR-DG-05 (not generated independently) — including event type, affected machine, duration, and a **`technician_notes` free-text column** (replaces a separate document corpus — see FR-SA-05). |
| FR-DG-07 | Generate firm sales order volume as **one continuous series spanning the full 3-year history plus an 8-week look-ahead** — not split into derived-history/generated-future. Linear trend (no compounding — avoids the exponential blowup a naive weekly-compounded rate would produce), per product/variant. The **8-week look-ahead follows a two-beat structure**, not a single spike: weeks 1-4 ramp EV Brake Caliper orders up while Engine Head stays flat (continuing its existing decline) — this is what drives crew priority toward Caliper in FR-DG-05a during this window; weeks 5-8 add a renewed Engine Head uptick (breaking its decline trend) on top of sustained Caliper demand, so both lines carry live demand pressure simultaneously by the second half. Ramps are gradual across each 4-week beat, not instant steps. No long-range (EDI 830-style) forecast is generated — out of MVP scope per BRD §2. |
| FR-DG-08 | Generate weekly inventory snapshots across the same full 3-year + 8-week scope as FR-DG-07: finished-goods buffer stays close to a target days-of-supply level historically (production tracks orders closely by construction, absent a breakdown), tightening during the look-ahead's EV spike window. Spare parts stock is tied to actual repair events from the sensor/CMMS simulation (FR-DG-05/06) — decremented per repair, replenished after lead time. |
| FR-DG-09 | *(Removed from MVP scope — was a standalone unstructured document corpus; superseded by FR-DG-06's `technician_notes` column. Retained as a future/stretch extension only.)* |
| FR-DG-10 | All historical data (FR-DG-01 through FR-DG-08, including orders/inventory — now generated on the same 3-year+8wk timeline, not derived) must cover 3 years ago → 30 days ago for the historical portion. The trailing 30 days of **sensor data** must be held back as pre-generated Parquet files, not bulk-loaded with the rest of history, and released one tick at a time via FR-PL-04b. Orders/inventory are not subject to this drip-feed — their look-ahead portion (next 8 weeks from "now") is simply generated and landed normally, no progressive release needed since they're weekly-grain, not 15-minute-tick. |
| FR-DG-11 | Data generation must produce right-censored records correctly: machines that have not failed by the end of the historical window must be labeled as censored (survival time unknown, only a lower bound), not assigned a synthetic failure time — required for FR-FS-04 (AFT training). |
| FR-DG-12 | All generation logic implemented as a Snowpark Python script (not a one-off notebook cell), parameterized (seed, date range, machine list) so it is re-runnable and adjustable without hand-editing generated data. Output is written as **Parquet files to a Snowflake Stage** (the landing zone), not CSV — subsequent load into Raw tables is a `COPY INTO`, not a dbt seed. |

## C. Data Pipeline (dbt + Raw/Standardized/Consumption + Dynamic Tables) — Functional Requirements

| ID | Requirement |
|---|---|
| FR-PL-00 | Ingestion (landing raw data into Snowflake) is **not** a dbt responsibility. The Snowpark generator (FR-DG-12) writes Parquet to a Stage; a `COPY INTO` loads each Raw table. dbt begins at Raw and owns only Raw → Standardized → Consumption. |
| FR-PL-01 | **Raw layer**: exact, unmodified copy of each Systems Landscape source (A1, A2, A4, A6, A7, A8), one Raw table per source, loaded via `COPY INTO` from Stage Parquet. No cleaning, no joining, no aggregation — Raw must be re-derivable byte-for-byte from the landed Parquet. A9 (model outputs) has no Raw table — see FR-PL-06. |
| FR-PL-02 | **Standardized layer**: cleansed, typed, conformed dimensions (equipment, calendar, product) and facts (sensor reading, maintenance event, order, inventory snapshot), built as dbt models on top of Raw. May join across Raw sources to conform keys/entities. **Must not aggregate** — grain stays identical to the Raw source (e.g., one row per sensor reading, not per hour). Standardized performs data-quality/timing joins only (e.g., the leakage-safe `hours_since_last_service`, FR-PL-03) — it does **not** normalize sensor values against machine baselines. Normalization is model-specific (depends on which baseline/scaling a given model wants) and belongs in the `FEAST` schema (FR-FS-01), not baked into a general-purpose fact that other consumers (dashboard, semantic view) should see in real physical units. |
| FR-PL-03 | Standardized layer must resolve "time since last service" per machine using a leakage-safe join: `service_end_ts < current_reading_ts` (strictly less-than), joined at the machine level (not per-sensor), even though restoration magnitude varies per sensor. This is a join, not an aggregation, so it belongs in Standardized, not Consumption. |
| FR-PL-04 | **Tick loading**: a scheduled Task runs `COPY INTO` on the Raw sensor landing table every 15 minutes (FR-DG-01a), loading whatever new Parquet file(s) are present at the Stage path — this is the Task's only job. `COPY INTO`'s native per-file load history makes repeated runs idempotent (FR-PL-09) without custom dedup logic. Downstream, the sensor path's Standardized and Consumption dbt models are materialized as **dynamic tables** (`materialized='dynamic_table'`, `target_lag='15 minutes'`), chained directly off the Raw landing table — no separate, manually-created Dynamic Table object outside dbt, and no action needed from the Task to propagate the refresh (the dynamic table engine watches its base table automatically). |
| FR-PL-04b | **Tick production (distinct from FR-PL-04)**: `COPY INTO` only loads files already sitting in the Stage — it does not create them. A separate step must place each new 15-minute Parquet micro-batch into the Stage *before* FR-PL-04's Task can pick it up. Pre-staging all 30 held-back days at once would defeat the drip-feed (a single `COPY INTO` would load everything immediately). Two production modes: (a) a background process uploads one pre-generated file per real 15-minute interval in the days before the event, building a genuine trailing window by demo day; (b) the demo script's manual trigger (FR-OPS-04) uploads the next file on demand *and* immediately fires the Task's `COPY INTO`, rather than waiting for the next schedule — this is what guarantees the live update moment during judging. A manual trigger path must exist for (b) regardless of whether (a) is also running. |
| FR-PL-04a | Materialization strategy: `dynamic_table` materialization is used for (a) the sensor path (Standardized sensor reading, lean Consumption atomic fact — no rolling windows there, see FR-FS-01/`FEAST`), (b) both model-inference Consumption tables (`fct_anomaly_result`, `fct_rul_prediction` — FR-FS-00b), and (c) the priority score (`fct_priority_score`, FR-FS-08) — it chains off `fct_rul_prediction` so a live tick propagates all the way through to the visible ranking, which is the point of the demo's priority-flip moment (BRD §7). `FEAST.FCT_SENSOR_FEATURES_INFERENCE` (FR-FS-01) is also a `dynamic_table` on this same 15-minute cadence, sitting between the lean Consumption fact and the model-inference tables. Dynamic tables can mix dynamic and plain-table sources (order/inventory stay static weekly tables) — Snowflake refreshes based on the fastest-changing source. All other domains use standard dbt table/view materialization, refreshed by the batch pipeline run steps (FR-OPS-02/02b) — running domains that change weekly as dynamic tables would waste credits for no benefit (NFR-01). |
| FR-PL-05 | **Consumption layer**: this is where all aggregation happens — dimension/fact tables (lean atomic grain for sensor readings, no rolling windows — see FR-FS-01/`FEAST` for that), OEE marts (weekly/monthly, by line), and (post-inference) anomaly, prediction, and prioritization marts (FR-FS-00 onward). |
| FR-PL-06 | **Superseded design note**: an earlier design assumed model inference ran outside dbt (a stored procedure/Task writing to a plain table), which would have required treating its output as a new Raw-equivalent input needing a thin Standardized re-entry pass before Consumption. That's no longer the case — inference now runs directly as a Consumption-layer dbt model calling the registered model in SQL (FR-FS-00b), so `cons.fct_anomaly_result` and `cons.fct_rul_prediction` **are** the Consumption fact tables, produced natively inside the dbt DAG. The priority score model (FR-FS-08) reads them the same way it reads any other Consumption table. |
| FR-PL-07 | Consumption OEE marts compute Availability from actual downtime/scheduled hours (BRD assumption 3); Quality % and Performance % are joined from fixed per-line constants, not computed from raw data. |
| FR-PL-08 | All dbt models must be tagged by layer (Raw/Standardized/Consumption) and have at least one dbt test (not_null / relationships / accepted_values as applicable) on key columns. |
| FR-PL-09 | Pipeline orchestration (Task/dbt run scheduling) must be resumable/idempotent — re-running a scheduled step must not duplicate rows or double-count events. |

## D. Feature Engineering & Model — Functional Requirements

| ID | Requirement |
|---|---|
| FR-FS-00 | **Anomaly detection**: train a single `IsolationForest` model using vibration, temperature, and RPM as joint input features (normalized against machine-specific baselines by the `sensor_rolling_features` macro, FR-FS-01 — not a pre-materialized Consumption column), across all 3 sensor-enabled machines in one model — a genuinely multivariate model that can catch combined-sensor patterns directly, not 3 independent per-sensor models. Training data is read from `FEAST.TRAINING_DATASET_ISO` (FR-FS-01) — not read directly from Consumption. **Verified at build time (2026-08-30, SH-22)**: `snowflake.ml.modeling.ensemble.IsolationForest`'s distributed `.fit(snowpark_df)` path spins up its own ephemeral nested stored procedure at runtime that does not inherit packages from the outer procedure (confirmed empirically — `ModuleNotFoundError: No module named 'pandas'` inside the generated procedure, unfixed by either the outer procedure's `PACKAGES` clause or `session.add_packages()`). At this project's data scale, trains plain `sklearn.ensemble.IsolationForest` on a `.to_pandas()` pull instead — scikit-learn is itself a directly-supported Model Registry built-in type, so registration/serving is unaffected. Revisit the distributed path if/when EPIC-FULLDATA's data volume makes an in-memory pull impractical. |
| FR-FS-00a | The model is registered and versioned in the Snowflake Model Registry (Snowpark ML Modeling is a supported built-in model type) alongside the RUL model — one consistent governance mechanism for both models, unlike a native SQL-object-based approach. Retrained periodically (e.g. weekly, for drift) as an ordinary new version, not a forced full-replace. |
| FR-FS-00b | **Inference — no Task, no stored procedure**: IsolationForest inference runs as a Consumption-layer dbt model materialized as a `dynamic_table` (`target_lag='15 minutes'`), whose `SELECT` calls the registered model directly — `MODEL(isolation_forest_model, LAST)!predict(...)` and `!decision_function(...)` — reading from `FEAST.FCT_SENSOR_FEATURES_INFERENCE` (FR-FS-01, not `cons.fct_sensor_reading` directly — that fact is lean/unnormalized, per Module 3). Snowflake's dynamic table engine re-scores only new rows on each refresh automatically; the 15-minute sensor tick (FR-PL-04) is what drives this refresh, there is no separately scheduled inference job. This correctness (predicting only the new tick, never re-deriving predictions for history) depends on FR-FS-01's backward-only rolling-window invariant holding as a true incremental refresh — see FR-FS-09. **Confirmed at build time (2026-08-30, SH-22)**: the registered model's exposed functions include `PREDICT`, `DECISION_FUNCTION`, `SCORE_SAMPLES`, and `EXPLAIN` — both target methods flagged as unverified are present, not just `decision_function`. |
| FR-FS-00e | **Historical backfill — automatic, not a separate step**: creating the anomaly inference dynamic table with `INITIALIZE = on_create` performs the full historical scoring pass itself as its initial load, over every row already in `cons.fct_sensor_reading` at creation time. This supersedes the earlier design, which assumed inference ran outside dbt and needed a manual one-time backfill job. |
| FR-FS-00f | Both models must be logged with `options={'volatility': Volatility.IMMUTABLE}` (`snowflake.ml.model.volatility.Volatility`) at `log_model` time. Built-in Snowpark ML Modeling types default to `IMMUTABLE` for deterministic methods, but **custom models default to `VOLATILE`** — and the RUL model is logged via the custom/generic Python path (raw `xgboost.Booster`), so this must be set explicitly. A `VOLATILE` method forces the calling dynamic table to do a full-table rescore on every refresh instead of an incremental one, which defeats the point of the 15-minute cadence. |
| FR-FS-00c | **Model explainability (pending validation)**: Snowflake Model Registry has a built-in, SHAP-based `explain` method for models logged with `enable_explainability` (default on) for supported packages — XGBoost, LightGBM, CatBoost, Scikit-learn, and their Snowpark ML Modeling equivalents, callable the same way as `predict`/`decision_function` (`MODEL(model_name, version)!explain(...)`, either inline in SQL or via `ModelVersion.run(..., function_name="explain")` in Python). Both the IsolationForest anomaly model (Scikit-learn-derived) and the RUL AFT model are candidates for this. **Two things must be validated during build, not assumed**: (1) whether `explain` behaves usefully for IsolationForest's anomaly-scoring output (vs. a standard predict target), and (2) whether it works for the RUL model given it's logged via the raw `xgboost.Booster` path rather than the standard high-level logging flow. Both models must be logged with `sample_input_data` (background data, up to 1,000 rows) to enable this. Document actual results once tested — do not treat as guaranteed. |
| FR-FS-00d | If FR-FS-00c validates successfully, expose a dedicated agent tool ("explain this prediction") that calls `MODEL(model_name, version)!explain(...)` (or `ModelVersion.run(input_row, function_name="explain")` from Python) for a specific machine/timestamp on request, returning per-feature Shapley contributions so the agent can answer "why did the model say this machine will fail" with the model's own attribution, not a paraphrase. If validation fails or is incomplete by build time, the fallback root-cause source is the raw per-sensor trend/deviation values shown alongside the anomaly score — documented as a graceful degradation path, not a blocker. |
| FR-FS-01 | **Feature engineering is reciprocated entirely in dbt — no external Feature Store SDK, no Entity/FeatureView/generate_training_set.** A new `FEAST` schema hosts one dbt macro, `sensor_rolling_features`, implementing rolling-window aggregation (1h/8h/24h/7d, over `cons.fct_sensor_reading`'s lean atomic grain) and baseline normalization (join to `cons.dim_sensor_baseline`) as a single reusable SQL definition. The macro is invoked from two models that differ only in materialization: `FEAST.FCT_SENSOR_FEATURES_INFERENCE` (`dynamic_table`, `target_lag='15 minutes'`, always fresh — feeds inference, FR-FS-00b/FR-FS-02) and `FEAST.FCT_SENSOR_FEATURES_TRAIN` (`table`, rebuilt once per training run, FR-OPS-02a — a frozen, reproducible snapshot so a training job isn't reading against a table mutating underneath it). The RUL model's feature set is a superset of the anomaly model's (it also consumes the anomaly model's output; the anomaly model does not consume its own output). Full macro/table design: LLD Module 4. |
| FR-FS-09 | **Correctness invariant — predict only new events, never re-derive history.** Every rolling-window feature in FR-FS-01's macro is backward-looking only (`ROWS BETWEEN N PRECEDING AND CURRENT ROW`), so a new tick's arrival changes only that tick's own output row — no earlier feature row, and therefore no earlier prediction row, is ever touched. This must hold as a genuine incremental dynamic-table refresh, not merely a functionally-correct-but-full-rescore fallback; if Snowflake's engine falls back to a full rescore, a downstream consumer could misinterpret "every row touched" as "every row is new" and re-run `predict()` across all of history on every tick. **Confirmed at the FEAST layer (2026-08-30, LLD Module 4 §2/§3)**: `FEAST.FCT_SENSOR_FEATURES_INFERENCE` achieves true `INCREMENTAL` refresh (`ALTER DYNAMIC TABLE ... REFRESH` returned `insertedRows:1, copiedRows:0` for a single new tick) — but this required an explicit fix (`immutable_where` frozen regions on `STD`/`CONS`, needed because their `ASOF JOIN` permanently forces `REFRESH_MODE=FULL`), not just the macro's backward-only shape alone. **Confirmed again one layer down (2026-08-31, SH-23/S-MODEL-3)**: `cons.fct_anomaly_result` also achieves true `INCREMENTAL` refresh (`insertedRows:1, copiedRows:0` for the same single-tick test, cascaded through all 4 layers) — see `docs/designs/5 - SH-23-inference-dynamic-table.md`. **Still open for `cons.fct_rul_prediction`** (separate future story, not yet built) — must be verified independently there too, not assumed to inherit. |
| FR-FS-02 | **Training only** is a Snowpark Python Stored Procedure using the native `xgboost` package directly — not the high-level Snowpark ML Modeling `XGBRegressor`, which does not expose the `label_lower_bound`/`label_upper_bound` DMatrix interface required for the AFT objective. Training reads `FEAST.TRAINING_DATASET_RUL` (FR-FS-01) and registers a new model version. **Inference is not a stored procedure**: it uses the same dynamic-table mechanism as FR-FS-00b — `MODEL(rul_model, LAST)!predict(...)` inside the Consumption dynamic table `cons.fct_rul_prediction`, reading from `FEAST.FCT_SENSOR_FEATURES_INFERENCE` (and the anomaly outputs, per FR-FS-01). Training never blocks or is blocked by inference — they run on entirely separate mechanisms (Python stored procedure vs. SQL dynamic table), not just separate schedules. |
| FR-FS-03 | Train/test split is time-based, not random: train on the earlier ~2.5 years of the historical window, test on the trailing ~6 months of history (still before the last-30-days live window) — prevents leakage of future degradation trend into training. Implemented as a `dataset_split` column computed directly in `FEAST.TRAINING_DATASET_RUL`/`TRAINING_DATASET_ISO` (FR-FS-01), not a separate filtering step. |
| FR-FS-04 | Model target is Remaining Useful Life (RUL) in operating hours, trained via XGBoost with `objective=survival:aft` inside the stored procedure from FR-FS-02, using engineered features including the anomaly detection outputs (FR-FS-00b) among its inputs. Labels are intervals: `(y_lower, y_upper)` = `(observed RUL, observed RUL)` for machines that failed (uncensored), or `(hours_survived_so_far, +inf)` for machines still running at window end (right-censored, per FR-DG-11). |
| FR-FS-05 | RUL model evaluation reports: concordance index (primary, survival-appropriate metric) on the full time-based test set, and MAE/RMSE on the uncensored subset only. Both the RUL model (as a custom/generic Python model wrapping the `xgboost.Booster`) and the anomaly detection model (FR-FS-00, a built-in Snowpark ML Modeling type) are registered and versioned in the same Snowflake Model Registry — see FR-FS-00c/00d for explainability status on each. |
| FR-FS-06 | Alert generation from model output requires smoothing — a prediction only becomes an actionable "high risk" alert after N-of-M consecutive high-risk evaluations (combining a sustained anomaly signal from FR-FS-00b with the RUL threshold), not on a single reading or a single anomaly flag. |
| FR-FS-07 | Predictions (predicted RUL hours, translated to calendar-day estimate via trailing utilization rate per BRD assumption 8) are computed directly by the `cons.fct_rul_prediction` dynamic table (FR-FS-02's inference mechanism) — this **is** the Consumption fact table itself, not a separate output requiring Raw/Standardized re-entry (FR-PL-06, superseded). |
| FR-FS-08 | A downstream SQL (dbt, Consumption-layer) model combines: predicted RUL (FR-FS-07) + firm near-term order volume (A6) + inventory buffer (A7) + spare-part readiness (A7) into a single explainable **priority score** per machine, using an explicit, documented weighted-sum formula (not a black box) — stated in the model documentation as an MVP placeholder for a future Monte Carlo/optimization approach (BRD §8). Materialized as a `dynamic_table` (FR-PL-04a), not a plain table, so the priority ranking itself updates live on each tick — not just the underlying RUL/anomaly numbers. |

| FR-OPS-02b | **Pipeline run, phase 2 (inference & downstream)**: invokes `dbt run`/`dbt test` on the model-inference dynamic tables (`cons.fct_anomaly_result`, `cons.fct_rul_prediction`) and anything downstream of them (priority score, FR-FS-08) — the tag excluded in FR-OPS-02.
