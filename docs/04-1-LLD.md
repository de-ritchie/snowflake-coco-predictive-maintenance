## CONS (Consumption)

Aggregation, dims/facts, marts happen here (FR-PL-05).

| Table | Columns | Grain | Materialization | Notes |
|---|---|---|---|---|
| `CONS.DIM_EQUIPMENT` | equipment_id, equipment_name, line_name, product_id, variant, is_sensor_enabled, throughput_units_per_hour, commissioned_ts | 1 row / equipment | `table` | = Semantic View `Machine` entity; product_id/variant FK to `CONS.DIM_PRODUCT`. `commissioned_ts` backs `hours_since_install` (Module 3) |
| `CONS.DIM_PRODUCT` | product_id, product_name, variant | 1 row / product / variant (4 rows total) | `table` | = Semantic View `Product` entity |
| `CONS.DIM_SENSOR_BASELINE` | equipment_id, sensor_type, baseline_mean, baseline_std | 1 row / equipment / sensor_type (9 rows total) | `table` | Module 2 §2's baseline parameters, as real data; consumed by the `FEAST` macro (Module 4) for normalization — not applied here |
| `CONS.FCT_SENSOR_READING` | equipment_id, reading_ts, sensor_type, reading_value, hours_since_last_service, hours_since_install | 1 row / equipment / sensor_type / tick | `dynamic_table`, `target_lag='15 minutes'` | = Semantic View `SensorReading` entity — **lean atomic fact**, raw value + operational-context joins only, real physical units. No rolling averages or normalization here — those are feature-engineering concerns, computed in `FEAST` (Module 4), not baked into the general-purpose fact |
| `CONS.FCT_ANOMALY_RESULT` | equipment_id, reading_ts, is_anomaly, anomaly_score, model_version | 1 row / equipment / tick | `dynamic_table`, `target_lag='15 minutes'` | `SELECT` calls `MODEL(isolation_forest_model, LAST)!predict/!decision_function(...)` directly (FR-FS-00b), reading from `FEAST.FCT_SENSOR_FEATURES_INFERENCE` (not `CONS.FCT_SENSOR_READING` directly — needs the rolling/normalized features) |
| `CONS.FCT_RUL_PREDICTION` | equipment_id, prediction_ts, predicted_rul_hours, predicted_rul_days, model_version | 1 row / equipment / tick | `dynamic_table`, `target_lag='15 minutes'` | `SELECT` calls `MODEL(rul_model, LAST)!predict(...)` directly (FR-FS-02) — reads `FEAST.FCT_SENSOR_FEATURES_INFERENCE` and `CONS.FCT_ANOMALY_RESULT` |
| `CONS.FCT_MAINTENANCE_EVENT` | equipment_id, event_type, event_start_ts, event_end_ts, duration_hours, technician_notes | 1 row / event | `table` | = Semantic View `MaintenanceEvent` entity |
| `CONS.FCT_ORDER` | product_id, variant, order_week, order_units | 1 row / product / variant / week | `table` | = Semantic View `Order` entity, FK to `CONS.DIM_PRODUCT`. Straight pass-through/rollup of `STD.SALES_ORDER` (full 3yr + 8wk, one continuous series — orders are the root input, not derived from production; see FR-DG-07). Firm near-term orders (EDI 862-style), not a long-range forecast |
| `CONS.FCT_INVENTORY_FG` | product_id, variant, period_week, fg_units_on_hand | 1 row / product / variant / week | `table` | = Semantic View `Inventory` entity (finished goods) |
| `CONS.FCT_INVENTORY_SPARE` | equipment_id, spare_part_name, period_week, units_on_hand, lead_time_days | 1 row / equipment / part / week | `table` | = Semantic View `Inventory` entity (spare parts) |
| `CONS.FCT_OEE` | line_name, period_week, availability_pct, performance_pct, quality_pct, oee_pct | 1 row / line / week | `table` | performance_pct, quality_pct are fixed constants (BRD assumption 3, FR-PL-07) |
| `CONS.FCT_PRIORITY_SCORE` | equipment_id, score_ts, rul_urgency, demand_pressure, inventory_buffer, spare_part_readiness, priority_score | 1 row / equipment / tick | `dynamic_table`, `target_lag='15 minutes'` | Formula per HLD §5 (FR-FS-08); chains off `CONS.FCT_RUL_PREDICTION` (dynamic) plus `CONS.FCT_ORDER`/`FCT_INVENTORY_*` (static) so a live tick propagates to the visible ranking |

## FEAST (dbt-native feature engineering — no Feature Store SDK)

Full design in Module 4. Listed here for completeness of the schema inventory:

| Table | Materialization | Role |
|---|---|---|
| `FEAST.FCT_SENSOR_FEATURES_INFERENCE` | `dynamic_table`, `target_lag='15 minutes'` | Rolling 1h/8h/24h/7d averages + z-score normalization over `CONS.FCT_SENSOR_READING`, via the `sensor_rolling_features` macro — **wide format**, one row per `(equipment_id, reading_ts)` with per-sensor-type columns (`vibration_z`, `temperature_z`, `rpm_z`, each with 4 rolling variants), pivoted from the long-format source so IsolationForest sees all 3 sensors jointly per tick. Always-fresh — this is what inference reads. |
| `FEAST.FCT_SENSOR_FEATURES_TRAIN` | `table` (rebuilt per training run) | Same macro, frozen snapshot — reproducible training input, immune to drift mid-run. |
| `FEAST.SPINE_MAINTENANCE_CYCLE` | `table` (training-only) | Per-cycle RUL label spine: equipment_id, cycle_end_ts, y_lower, y_upper (moved from Consumption — a training artifact, not a general business fact). |
| `FEAST.TRAINING_DATASET_RUL` | `table` | Spine ASOF-joined to `FCT_SENSOR_FEATURES_TRAIN`, plus `dataset_split` (train/test, FR-FS-03). |
| `FEAST.TRAINING_DATASET_ISO` | `table` | Unsupervised slice of `FCT_SENSOR_FEATURES_TRAIN`, plus `dataset_split`. |
