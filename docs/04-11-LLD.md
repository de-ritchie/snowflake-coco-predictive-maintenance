# LLD Module 11 — SDLC Custom Skills
## SnowComotive — Predictive Maintenance & Overall Equipment Effectiveness (OEE) Command Center

Status: Draft v0.1
Traces to: [02-FRD.md](02-FRD.md) Section H (FR-SDLC-01/02/03) | [03-HLD.md](03-HLD.md) §3

Four skills, **scoped specifically to dbt model development** (Raw/Standardized/Consumption/`FEAST` — Modules 1/3/4) — not Snowpark scripts, which use the already-bundled `snowpark-python` skill instead (no custom skill needed there, confirmed this module). Each is manually invoked, one Jira story at a time, none chains automatically to the next (FR-SDLC-02).

---

## 1. Design agent

**Input**: a Jira story (Kanban project A10) describing a dbt model to build/change.
**Does**: reads the relevant LLD module (1/3/4, whichever the story touches) and the existing dbt project structure, then produces a short design note — which Consumption/`FEAST` table(s) are affected, the exact SQL shape (joins, materialization, macro usage if relevant), and which existing FR-ID/LLD section it traces to. Does **not** invent new architecture — if the story needs something the LLD doesn't already specify, the design note says so explicitly and stops, rather than guessing.
**Output**: a design note (markdown, attached to the Jira story) — not code yet.
**Human gate**: user reviews the design note before authorizing the Developer agent to proceed.

## 2. Developer agent

**Input**: the story + Design agent's note.
**Does**: writes the actual dbt model SQL file (and macro, if the story touches `FEAST`), plus its `schema.yml` entry (layer tag, at least one test per FR-PL-08). Follows the naming/materialization conventions already fixed in Modules 1/3/4 (e.g., `dynamic_table` + `target_lag='15 minutes'` for anything in the sensor path, `RAW`/`STD`/`CONS`/`FEAST` schema prefixes) — doesn't re-derive these per story, just applies them.
**Output**: a git branch/PR with the new/changed `.sql` + `.yml` files.
**Human gate**: none at this step — the PR itself is the checkpoint, reviewed next.

## 3. Reviewer agent

**Input**: the Developer agent's PR.
**Does**: runs `dbt run --select <model>+` and `dbt test` against the changed model and its downstream dependents; checks the PR against the story's acceptance criteria and the LLD section it traces to (e.g., for a sensor-path change, specifically checks the leakage-safety and incremental-refresh properties called out in Module 3 §3/Module 4 §3 — not just "does it run"). Flags anything that silently regresses a documented invariant.
**Output**: pass/fail + inline PR comments. Does **not** merge — that's a human action.
**Human gate**: user reads the review, decides whether to merge.

## 4. Documenter agent

**Input**: a merged PR.
**Does**: updates dbt-level documentation only — `schema.yml` column/model descriptions (feeding `dbt docs generate`) and a running build changelog. Does **not** rewrite the BRD/FRD/HLD/LLD documents themselves (those are this project's design record, already complete; the Documenter's job is keeping the *build artifact's* docs in sync with what actually got merged, which can drift from the design as implementation details get resolved).
**Output**: updated `schema.yml` descriptions + a changelog entry.
**Human gate**: none required — low-risk, additive documentation update; user can always amend.

## Governance recap (FR-SDLC-02, unchanged from FRD — restated for this module's completeness)

Design → Develop → Review → Document, one story at a time, human merges the PR and moves the Kanban card to Done. No agent invokes the next one automatically — this is the explicit human-gated evidence of CoCo's lifecycle usage for judging (BRD §9).

---

## Reuse (FR-SDLC-03)

All four are authored as standalone, documented CoCo skills (`SKILL.md` + frontmatter, per the platform's skill format) — reusable on any dbt project, not hardcoded to SnowComotive's specific tables. The scope-narrowing decision this module made (dbt-only, not Snowpark) actually *helps* reusability: a skill that only needs to reason about dbt model conventions generalizes more cleanly than one that also has to know when to write a Snowpark script instead.
