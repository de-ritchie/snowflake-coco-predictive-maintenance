# LLD Module 11 — SDLC Agent & Skill Toolkit
## SnowComotive — Predictive Maintenance & Overall Equipment Effectiveness (OEE) Command Center

Status: Draft v0.3 — reworked 2026-08-29 to merge board-triage + the non-dbt executor into one agent
Traces to: [02-FRD.md](02-FRD.md) Section H (FR-SDLC-01/02/03) | [03-HLD.md](03-HLD.md) §3

**Superseded design note (2026-08-26)**: originally specified as 4 CoCo *skills*. Reworked to 5 real Sonnet-5 subagents (own isolated context, dispatched via the `task` tool, `.snowflake/cortex/agents/*.md`) plus a 6th bootstrapping agent (`Genesis-agent`), backed by 2 skills that held only the purely mechanical, repeatable procedures. Rationale: skills inject markdown into the *same* conversation with no isolated context or real dispatch; agents are where actual judgment/reasoning work belongs — "agents are the powerhouse where skills are applied."

**Superseded again (2026-08-29)**: the original design had two separate implementation lanes — a 4-stage `Design→Developer→Reviewer→Documenter` chain for dbt-model stories only, and a 5th general-purpose executor agent for everything else (Snowpark/Streamlit/ops/agent-config/Jira work), plus a *separate* `board-triage` **skill** that decided backlog priority and dispatched the right lane. Three problems with that shape, all fixed here:
1. `board-triage` (a skill — no isolated context, no real judgment per this project's own skill/agent split) was nonetheless doing real judgment work (deciding what's next, discussing dependencies with the user) — a skill/agent category mismatch.
2. The general-purpose executor agent was originally also named `Triage-agent`, colliding with the `board-triage` skill name despite doing something completely unrelated — this needed constant "not to be confused with" disclaimers across the doc set, itself a sign the design was wrong, not just the naming.
3. Content agents (`Developer-agent`/`Documenter-agent`/the old executor) each independently committed, opened PRs, and transitioned Jira status — scattering git/Jira mutation across multiple agents instead of centralizing it.

**Current design**: `board-triage` is retired. Its judgment logic and the old executor's PR/Review/Done responsibilities merge into one agent, **`Jira-Triage-agent`** — the sole agent in this project that ever touches Jira or mutates git state (branch/commit/push/PR/comment/status-transition). The 4 content agents (`Design-agent`/`Developer-agent`/`Reviewer-agent`/`Documenter-agent`) now apply uniformly to **any** story type, not just dbt models — there is no separate non-dbt lane anymore, and no story-type routing decision to make. Four of the five SDLC agents remain strictly content-only (never touch Jira/git); the 5th, `Jira-Triage-agent`, never writes implementation content (no SQL, no Streamlit, no design docs). `Genesis-agent` is the 6th, unrelated to per-story work — it bootstraps brand-new projects.

**Critical constraint driving this whole design**: subagents cannot spawn other subagents. There is no orchestration skill/agent auto-sequencing Design→Developer→Reviewer→Documenter→Jira-Triage — the user drives every step manually, one agent at a time, looping through content agents as many times as needed before ever invoking `Jira-Triage-agent` (FR-SDLC-02).

**Table-agnostic by design**: none of the 5 SDLC agent prompts hardcode a specific table/column/schema/FR-ID. Specifics always come from `docs/03-HLD.md` / the relevant `docs/04-*-LLD.md` module, or the frozen per-story design doc once one exists — this is also what lets `Genesis-agent` copy these agent files verbatim into a different project without editing them.

## 1. Design-agent

**Input**: a story (of any type — dbt model, Streamlit page, Snowpark script, agent/tool config, ops script) describing what to build/change, relayed by the user or visible from context — this agent never queries Jira itself.
**Does**: reads the relevant HLD/LLD section(s) (check `docs/04-0-LLD.md`'s index for which module covers what) and the existing repo structure for that domain, then **brainstorms interactively with the user** (non-autonomous — genuinely back-and-forth, not just a one-shot read-and-write) about the implementation shape and any named correctness invariant the FRD/LLD calls out for this kind of change. Does **not** invent new architecture — if the story needs something the docs don't already specify, says so explicitly and stops rather than guessing. **Never freezes without the user's explicit confirmation.** Optional for genuinely trivial stories, at the user's discretion.
**Output**: a frozen design doc at `docs/designs/SH-<key>-<slug>.md` — not code yet, and no Jira touch (writing this file is content work; posting about it is `Jira-Triage-agent`'s job, later, folded into its single consolidated comment).
**Human gate**: the freeze confirmation itself; the user reviews the frozen doc before authorizing `Developer-agent` to proceed.

## 2. Developer-agent

**Input**: the story + `Design-agent`'s frozen doc (`docs/designs/SH-<key>-*.md`), if one exists.
**Does**: implements strictly against that frozen doc — whatever the story's domain calls for (dbt model SQL + macro + `schema.yml`, a Streamlit page, a Snowpark script, an agent tool-spec/prompt, an ops SQL block). Follows whatever naming/materialization/layout conventions the design doc and HLD/LLD establish — doesn't re-derive or assume them from a prior project. If reality diverges from the frozen doc (something in it doesn't actually work), stops and tells the user rather than silently implementing something different.
**Output**: new/changed files, left **uncommitted** on disk. No git touch (no commit, no branch creation — it confirms it's on the right branch via a read-only `git branch --show-current` check, but if the branch doesn't exist yet it tells the user to invoke `Jira-Triage-agent` rather than creating one itself), no Jira touch.
**Human gate**: none at this step.

## 3. Reviewer-agent

**Input**: `Developer-agent`'s changes, currently on disk — committed or not, it doesn't matter.
**Does**: reviews the **working-tree diff** (`git diff main`, or `git diff main...<branch>` plus any further uncommitted changes on top — whichever reflects everything since the story started; no commit is ever required first) against the frozen design doc and whatever named correctness invariants this project's FRD/LLD actually calls out for that area (e.g. a join-timing/leakage rule, a windowing-direction rule for incremental computations, a materialization requirement) — not just "does it run." Runs `dbt run --select <model>+`/`dbt test` for dbt work, or whatever verification fits the artifact otherwise. The point is design adherence, bugs, code quality, and test coverage — the diff is just the lens, not the point. Explicitly states whether the design doc itself needs updating to match a legitimate, agreed deviation. **Stateless and re-invokable any number of times** — call it again after another round of edits and it just re-reviews whatever's currently on disk.
**Output**: pass/fail with specifics, reported **in chat only** — not a Jira comment (that would duplicate `Jira-Triage-agent`'s single consolidated comment later) and not a PR comment (none exists yet at this stage). Does **not** edit code, does **not** commit, does **not** merge.
**Human gate**: user reads the review, decides whether the story is ready for `Documenter-agent` or needs another `Developer-agent` pass.

## 4. Documenter-agent

**Input**: `Reviewer-agent`'s findings (from chat context) + the frozen design doc, if one exists.
**Does**: reconciles the design doc with what was actually built (updates it and says so explicitly if implementation legitimately diverged — never silently documents the new state as if it was always the plan), updates `schema.yml` descriptions (for dbt work) + `CHANGELOG.md`.
**Output**: reconciled design doc (if changed) + updated `schema.yml`/`CHANGELOG.md`, left **uncommitted**. No PR, no Jira comment, no status change — all of that is `Jira-Triage-agent`'s job now, invoked separately whenever the user is ready, not automatically after this stage.
**Human gate**: the user decides when to invoke `Jira-Triage-agent` next — possibly not immediately; they may loop back through `Developer-agent`/`Reviewer-agent` again first.

## 5. Jira-Triage-agent

**Input**: whichever checkpoint the user invokes it for — there is no fixed single-shot workflow.
**Does**: the *only* agent that ever touches Jira or mutates git state, across the whole project:
- **Front door**: queries the board via JQL (`dev-workflow` skill), discusses priority/dependencies with the user, confirms the next story, transitions it to In Progress, creates its branch — then stops and hands back.
- **Mid-flow**: on request ("commit this"), stages and commits whatever's currently in the working tree, with a message referencing the Jira key(s). Callable any number of times, at any point, regardless of which content agent(s) produced the changes.
- **Back door**: on request, opens the PR, posts **one** consolidated Jira comment (design doc path + review summary + PR link — not one comment per stage), transitions the story to Review.
- **Closing**: once the user confirms the PR merged, transitions Review→Done, then re-runs its own Epic-selection logic for the next story.
**Output**: depends on which checkpoint — a branch, a commit, an open PR + Jira comment + Review status, or a Done transition. Never writes implementation content (no SQL, no Streamlit, no design docs) — that's the 4 content agents' job.
**Human gate**: every checkpoint above is user-invoked, not automatic; merging the PR is the user's action, never this agent's.

## 6. Genesis-agent (bootstrapping, distinct from the 5 above)

Not part of the per-story SDLC chain — this is what creates a *new* project's `docs/*.md` stack from scratch, since everything above assumes it already exists. Brainstorms a brand-new problem statement with the user through cascading freeze checkpoints (BRD → FRD → HLD → LLD, module by module — the module breakdown itself is brainstormed too, not assumed fixed at any particular count), writing each frozen stage to `docs/01-BRD.md` through `docs/04-<N>-LLD.md`. Once LLD is frozen, optionally scaffolds genericized copies of the 5 agents above + the `dev-workflow` skill + a fresh `AGENTS.md` into the new project — this is what makes the whole toolkit reusable beyond this one repo, not just this one demo (BRD §8's scalability claim).

**Known limitation**: `dev-workflow` still hardcodes *this* project's Jira cloudId/project key in prose. `Genesis-agent`'s scaffold step copies it with placeholders for a new project's Jira details rather than a clean single-config-file parameterization — a documented gap, not silently glossed over.

Explicitly out of scope for `Genesis-agent`: the Epics/Stories/Tasks backlog breakdown (this repo's `docs/05-Epics.md` equivalent) — that stays a manual, collaborative follow-up after the docs are frozen.

## Governance recap (FR-SDLC-02, unchanged from FRD)

Design → Develop → Review → Document, one story at a time, looped through as many times as needed, then `Jira-Triage-agent` commits/opens the PR/transitions status on request — human merges the PR and confirms it, `Jira-Triage-agent` moves the Kanban card to Done. No agent invokes the next one automatically (technically enforced, not just a convention — subagents cannot spawn other subagents) — this is the explicit human-gated evidence of CoCo's lifecycle usage for judging (BRD §9).

## Reuse (FR-SDLC-03)

All 6 agents (`.snowflake/cortex/agents/*.md`) and the 1 skill (`.cortex/skills/dev-workflow/SKILL.md`) are genericized — none hardcode this project's specific FR-IDs, table names, or macro names (a real leakage bug found and fixed 2026-08-26: the agents originally claimed to be "table-agnostic" while still referencing this project's `FR-PL-03`/`FR-FS-09`/`FEAST.sensor_rolling_features`/`RAW/STD/CONS/FEAST` inline). `Genesis-agent` is the concrete reuse mechanism — it copies these files as-is into a new project rather than requiring manual editing first.
