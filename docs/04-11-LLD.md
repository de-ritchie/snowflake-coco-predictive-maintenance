# LLD Module 11 — SDLC Agent & Skill Toolkit
## SnowComotive — Predictive Maintenance & Overall Equipment Effectiveness (OEE) Command Center

Status: Draft v0.2 — reworked 2026-08-26 to match actual implementation
Traces to: [02-FRD.md](02-FRD.md) Section H (FR-SDLC-01/02/03) | [03-HLD.md](03-HLD.md) §3

**Superseded design note**: originally specified as 4 CoCo *skills*. Reworked to 5 real Sonnet-5 subagents (own isolated context, dispatched via the `task` tool, `.snowflake/cortex/agents/*.md`) plus a 6th bootstrapping agent (`Genesis-agent`), backed by 2 skills that hold only the purely mechanical, repeatable procedures. Rationale: skills inject markdown into the *same* conversation with no isolated context or real dispatch; agents are where actual judgment/reasoning work belongs — "agents are the powerhouse where skills are applied." Four of the five SDLC agents remain **scoped specifically to dbt model development** (Raw/Standardized/Consumption/`FEAST` — Modules 1/3/4); everything else routes to the 5th, `Triage-agent`.

**Critical constraint driving this whole design**: subagents cannot spawn other subagents. There is no orchestration skill/agent auto-sequencing Design→Developer→Reviewer→Documenter — the user drives that manually, one agent at a time, invoking each stage explicitly (FR-SDLC-02).

**Table-agnostic by design**: none of the 5 SDLC agent prompts hardcode a specific table/column/schema/FR-ID. Specifics always come from `docs/03-HLD.md` / the relevant `docs/04-*-LLD.md` module, or the frozen per-story design doc once one exists — this is also what lets `Genesis-agent` copy these agent files verbatim into a different project without editing them.

---

## 1. Design-agent

**Input**: a Jira story (Kanban project A10) describing a dbt model to build/change.
**Does**: reads the relevant LLD module(s) (check `docs/04-0-LLD.md`'s index for which module covers what) and the existing dbt project structure, then **brainstorms interactively with the user** (non-autonomous — genuinely back-and-forth, not just a one-shot read-and-write) about which table(s) are affected, the SQL shape (joins, materialization, macro usage if relevant), and any named correctness invariant this project's FRD/LLD calls out. Does **not** invent new architecture — if the story needs something the LLD doesn't already specify, says so explicitly and stops rather than guessing. **Never freezes without the user's explicit confirmation.**
**Output**: a frozen design doc at `docs/designs/SH-<key>-<slug>.md`, attached to the Jira story as a comment (via the `dev-workflow` skill) — not code yet.
**Human gate**: the freeze confirmation itself; the user reviews the frozen doc before authorizing `Developer-agent` to proceed.

## 2. Developer-agent

**Input**: the story + `Design-agent`'s frozen doc (`docs/designs/SH-<key>-*.md`).
**Does**: implements strictly against that frozen doc — writes the actual dbt model SQL file (and macro, if the story touches a shared feature-engineering macro), plus its `schema.yml` entry (layer tag, at least one test per this project's dbt-testing requirement). Follows whatever naming/materialization conventions the design doc and HLD/LLD establish — doesn't re-derive or assume them from a prior project. If reality diverges from the frozen doc (something in it doesn't actually work), stops and tells the user rather than silently implementing something different.
**Output**: new/changed `.sql` + `.yml` files, committed to the story's branch (created via the `dev-workflow` skill's naming convention). **No PR, no Jira status change** — that's `Documenter-agent`'s job, after `Reviewer-agent` has checked the work.
**Human gate**: none at this step.

## 3. Reviewer-agent

**Input**: `Developer-agent`'s committed changes on the story's branch. **No PR exists yet at this stage** (that's opened later, by `Documenter-agent`).
**Does**: runs `dbt run --select <model>+` and `dbt test` against the changed model and its downstream dependents; checks the implementation against the frozen design doc and whatever named correctness invariants this project's FRD/LLD actually calls out for that area (e.g. a join-timing/leakage rule, a windowing-direction rule for incremental computations, a materialization requirement) — not just "does it run." Explicitly states whether the design doc itself needs updating to match a legitimate, agreed deviation.
**Output**: pass/fail with specifics, posted as a Jira comment (via `dev-workflow`) and summarized in chat — not a PR comment, since none exists yet. Does **not** edit code, does **not** merge.
**Human gate**: user reads the review, decides whether the story is ready for `Documenter-agent`.

## 4. Documenter-agent

**Input**: `Reviewer-agent`'s findings + the frozen design doc.
**Does**: reconciles the design doc with what was actually built (updates it and says so explicitly if implementation legitimately diverged — never silently documents the new state as if it was always the plan), updates `schema.yml` descriptions + `CHANGELOG.md`. **Then, unlike the original design, this agent itself opens the PR and moves the story to Review** (via `dev-workflow`'s `gh pr create` + status-transition procedures) — this was moved here from an earlier draft that had Developer/board-triage own the PR step, so that the PR reflects fully-reconciled documentation, not just working code.
**Output**: reconciled design doc (if changed), updated `schema.yml`/`CHANGELOG.md`, a Jira comment with the final doc, an open PR, the story in Review status.
**Human gate**: the user merges the PR when ready and tells the assistant — moving Review→Done happens then, via the `board-triage` skill, not this agent.

## 5. Triage-agent

**Input**: any story that is NOT `sdlc-skill`-labeled (i.e. not one of the four dbt-model stages above) — `ops`/`snowpark`/`streamlit`/`agent`/`jira`/`machine-learning` labels.
**Does**: the full branch→implement→PR→Review cycle itself, in one pass — no separate design-doc-freeze step required (may still write a short optional design note for non-trivial work), no separate Design/Developer/Reviewer/Documenter split. This exists because most non-dbt-model work (environment scripts, the Snowpark data generator, Streamlit pages, agent/tool config, Jira integration code) doesn't need the heavier 4-stage treatment — the HLD/LLD/FRD already specify what's needed, and there's no shared schema/materialization-convention risk the way there is across dbt models.
**Output**: implemented change, open PR, story in Review. Distinct from the `board-triage` **skill** (which only discusses backlog priority and dispatches — never implements).
**Human gate**: same as `Documenter-agent` — user merges, tells the assistant, `board-triage` moves it to Done.

## 6. Genesis-agent (bootstrapping, distinct from the 5 above)

Not part of the per-story SDLC chain — this is what creates a *new* project's `docs/*.md` stack from scratch, since everything above assumes it already exists. Brainstorms a brand-new problem statement with the user through cascading freeze checkpoints (BRD → FRD → HLD → LLD, module by module — the module breakdown itself is brainstormed too, not assumed fixed at any particular count), writing each frozen stage to `docs/01-BRD.md` through `docs/04-<N>-LLD.md`. Once LLD is frozen, optionally scaffolds genericized copies of the 5 agents above + the 2 supporting skills + a fresh `AGENTS.md` into the new project — this is what makes the whole toolkit reusable beyond this one repo, not just this one demo (BRD §8's scalability claim).

**Known limitation**: `board-triage`/`dev-workflow` still hardcode *this* project's Jira cloudId/project key/label taxonomy in prose. `Genesis-agent`'s scaffold step copies them with placeholders for a new project's Jira details rather than a clean single-config-file parameterization — a documented gap, not silently glossed over.

Explicitly out of scope for `Genesis-agent`: the Epics/Stories/Tasks backlog breakdown (this repo's `docs/05-Epics.md` equivalent) — that stays a manual, collaborative follow-up after the docs are frozen.

## Governance recap (FR-SDLC-02, unchanged from FRD)

Design → Develop → Review → Document, one story at a time, human merges the PR and moves the Kanban card to Done. No agent invokes the next one automatically (technically enforced, not just a convention — subagents cannot spawn other subagents) — this is the explicit human-gated evidence of CoCo's lifecycle usage for judging (BRD §9).

---

## Reuse (FR-SDLC-03)

All 6 agents (`.snowflake/cortex/agents/*.md`) and 2 skills (`.cortex/skills/*/SKILL.md`) are genericized — none hardcode this project's specific FR-IDs, table names, or macro names (a real leakage bug found and fixed 2026-08-26: the agents originally claimed to be "table-agnostic" while still referencing this project's `FR-PL-03`/`FR-FS-09`/`FEAST.sensor_rolling_features`/`RAW/STD/CONS/FEAST` inline). `Genesis-agent` is the concrete reuse mechanism — it copies these files as-is into a new project rather than requiring manual editing first.

## Deferred to build time

- Whether `Reviewer-agent`'s acceptance-criteria check is fully automated or partially manual (e.g., checking a named invariant programmatically vs. reasoning about it from the LLD text) — likely a mix, refine once actually exercised on a real story.
- The synthetic data generator as its own standalone, generalized reusable skill — explicitly deferred (not this submission's scope); for now, the data generator (Module 2) is built directly using the bundled `snowpark-python` skill, following Module 2's spec as-is.
- A clean config-file parameterization for `board-triage`/`dev-workflow`'s Jira specifics (see `Genesis-agent`'s known limitation above) — copy-and-fill-in-placeholders is the current state, not a blocker for this submission.
