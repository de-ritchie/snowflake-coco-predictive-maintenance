## 2. Duplicate-ticket check (FR-JR-04) — the actual logic

Runs at the top of `SP_CREATE_JIRA_TICKET`, before any create call:

```python
def sp_create_jira_ticket(session, equipment_id, predicted_rul_hours, priority_score, root_cause_summary, requested_by_persona):
    # Step 1: live JQL check — not a local mirror table (no ticket-history table exists per BRD §5.3;
    #   the agent only creates tickets going forward, so Jira itself is the single source of truth)
    jql = (
        f'project = SM AND labels = "equipment:{equipment_id}" '
        f'AND (status not in (Closed, Resolved, Done) '
        f'OR resolutiondate >= "-{RECENT_CLOSED_WINDOW_HOURS}h")'
    )
    existing = jira_client.search_issues(jql, max_results=1)

    if existing:
        issue = existing[0]
        status = "ALREADY_OPEN" if issue.fields.status.name not in CLOSED_STATUSES else "RECENTLY_CLOSED"
        return {"status": status, "ticket_id": issue.key, "ticket_url": f"{JIRA_BASE_URL}/browse/{issue.key}"}

    # Step 2: no match — create
    new_issue = jira_client.create_issue(fields={...})   # §1's field mapping
    return {"status": "CREATED", "ticket_id": new_issue.key, "ticket_url": f"{JIRA_BASE_URL}/browse/{new_issue.key}"}
```

**Why a `labels` filter, not a custom field, for the machine-identity match**: Jira labels are queryable in JQL without needing a custom-field schema change on the SM project beforehand — `equipment:{equipment_id}` as a label, set at creation time, is enough to filter by machine. Simpler than provisioning and maintaining a dedicated Jira custom field just for this lookup.

**`RECENT_CLOSED_WINDOW_HOURS`**: tunable, deferred to build time — 24h is a reasonable MVP default (long enough that closing-then-immediately-reopening within the same shift doesn't spam, short enough that a genuinely new failure weeks later isn't suppressed). Not tied to Module 2's maintenance-cycle concept (that's generator-internal simulation state, not something the live stored procedure has access to at runtime against real Jira).

## 3. Auth mechanism

Jira REST API v3, authenticated via API token (Jira Cloud) stored as a Snowflake **Secret** object, referenced by the stored procedure's external access integration — not embedded in code or agent instructions. Setup script (FR-OPS-01) provisions the secret once per environment; teardown (FR-OPS-05) does not remove it (external credential, manual cleanup, matching FR-OPS-05's existing stance on the Jira project itself).

```sql
CREATE OR REPLACE SECRET jira_api_token
  TYPE = GENERIC_STRING
  SECRET_STRING = '<token>';   -- set via setup script parameter, not hardcoded

CREATE OR REPLACE NETWORK RULE jira_network_rule
  TYPE = HOST_PORT
  MODE = EGRESS
  VALUE_LIST = ('<jira-instance>.atlassian.net:443');

CREATE OR REPLACE EXTERNAL ACCESS INTEGRATION jira_access_integration
  ALLOWED_NETWORK_RULES = (jira_network_rule)
  ALLOWED_AUTHENTICATION_SECRETS = (jira_api_token)
  ENABLED = TRUE;
```

`SP_CREATE_JIRA_TICKET` is created `EXTERNAL_ACCESS_INTEGRATIONS = (jira_access_integration)`, `SECRETS = ('jira_token' = jira_api_token)` so it can call out to Jira's REST API from within the Python stored procedure.
